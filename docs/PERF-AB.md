## 5. 方法论与预登记阈值（设计 §3 全文口径，跑前登记、可 falsify）

1. 双栈常驻、按轮交替（GGG 与 RRR 同起，G,R,G,R,G,R 交替发轮消时段漂移；空闲
   对端巡检在跑，声明计入噪声带）；每轮记录 loadavg；端口结构同构、端口号不同。
2. 轮 = 同一会话内一次 speedtest::run（Rust = 独立 speedtest 动词 --rounds；Go =
   daemon 会话内 speedtest CLI）；每轮自带 2s warmup；两侧参数同构（10s/10s/4 流，
   Go DefaultParams = Rust Params::default 已核对同值）。
3. 构建口径：Rust release；Go = baseline 克隆构建（GOTOOLCHAIN=go1.24.5 基线门）。
4. 尾延迟 = echo RTT（经隧道单连接 200 次回显往返；python 测量器走客户端本地转发口，
   两链路同一脚本——差异只在隧道两侧实现栈）。
5. RSS = 1Hz `ps -o rss=` 测量期取 max + 就绪稳态两口径；三角色各自 pid。
6. 体积两口径（原始 / strip）。
7. **预登记阈值**：吞吐中位比值 Rust/Go ∈ [0.5, 2.0]；echo RTT 中位差 ≤ 2ms 或
   ≤50%；RSS 比值 ≤ 4×；体积报比值。超阈处置 = 复测一轮 → 仍超则 §6 归因挂账
   （R5 量化不优化）。

## 6. 归因挂账（超阈两项，复测确认后登记；R5 量化不优化）

1. **下行吞吐 0.42×（超阈 [0.5, 2.0]）**——缺口定位 = Rust 出口 bulk 发送路径：
   六链路 E13 一致显示 Rust 出口当发送方时 down ≈ 255–285 vs Go ≈ 450–680，而
   上行（客户端发送）两侧接近。R3 期即有同量级记录（Rust↔Rust 250–263）——非
   本批回归，是实装以来一贯量级。候选归因面：speedtest 服务端发送泵的批量化/
   flush 粒度、smoltcp TX 队列水位参数、WG 封装批大小。**深挖归 R6 前置批/R8
   终测**（真机口径下重标定后再议优化）。
2. **echo RTT 中位差 ≈ 6.3ms（两项超阈）**——Rust portfwd → Rust exit 路径的
   固有唤醒粒度（R1 决议：自管线程 + poll(2)——事件等待靠 poll 超时拍/管道唤醒，
   vs Go goroutine 即时调度）。p95/p99 紧随 p50（7.0ms 带内）说明是**恒定处理
   粒度不是抖动**。对使用面影响：交互式会话（term）每击键回显 ~6ms——远低于
   人感阈值；优化候选（poll 拍加密/事件驱动唤醒）登记 R8。

## 7. 结论行（每维一句）

- 吞吐：**up 界内（0.53×）、down 0.42× 超阈挂账**——缺口在 Rust 出口发送路径，非回归，R6/R8 深挖。
- 延迟：**RTT 恒定 +6.3ms 超阈挂账**——poll(2) 唤醒粒度的设计代价，p99 带内稳定。
- RSS：**PASS（0.02–0.20×，全面显著更小）**。
- 体积：**PASS（0.16×；dylib 口径待 R7 复测）**。

## 8. R6 前置批 ⑤ 修正（2026-10-03 深夜重测，本节为 §1 吞吐的**现行口径**）

**§1 的 down 0.42× 撤销——根因 = 同机拓扑的 endpoint 采纳 artifact，非实现栈差距。**

- **机制**：同机部署下出口按网卡自报端点（token 含 LAN IP 如 192.168.3.12），客户端
  赛跑随机采纳；采纳 LAN IP 时两侧每包 UDP sendto 走 en0 环回路径——微基准实测
  **18.3µs/包 vs lo0 5.5µs/包（3.3 倍）**（`/tmp` 下 C 微基准，1280B×200k 包）。
  R5 轮的 RRR 会话恰好采纳 LAN IP、GGG 恰好采纳 lo0，0.42× 主要是这个不对称。
- **重测口径（tools/perf-ab.sh v2）**：两侧 token 一律铸 `--loopback-only` 变体
  （Direct 端点非回环 IPv4 → 127.0.0.1 同端口），公平对照 = 同走 lo0；每轮加直连
  断言（speedtest 输出的「via=… 开跑时冻结」行，非直连轮作废重跑，两次仍中继即中止）。
- **重测数据（3+3 交替轮，中位 Mbps）**：

| 侧 | down | up |
|---|---|---|
| GGG | 670（670/666/680） | 757（693/757/801） |
| RRR | 529（528/529/541） | 1054（1035/1054/1057） |
| **Rust/Go** | **0.79（界内 ✓）** | **1.39（界内 ✓）** |

- **四维结论更新**：吞吐两维全部界内（预登记阈值 [0.5, 2.0]）——§6.1 的
  「Rust 出口 bulk 发送路径缺口」挂账**关闭**。RTT/RSS/体积结论不变。
- **次因登记（真机口径优化候选，归 R8）**：Rust 出口单驱动线程串行
  （采样：76% sendto + 10.5% WG encapsulate + ~2% 栈 poll——下行 bulk 时单核上限）；
  Go 出口收/加密/发送多 goroutine 并行。真机 Linux/OHOS 侧有 sendmmsg 批量发送
  可用（macOS 无），加上并行 encap 是 R8 终测的优化面。
- **RSS 口径补全（R5 中-6 整改）**：Rust 轮的独立 speedtest CLI 进程已纳入 1Hz 采样
  （`rrr-client-cli` 行，峰值 16.8MB——非常驻口径，单列呈现）。

## 9. 瓶颈归因（R8-2，2026-10-05 凌晨：分层测量 + 2×2 矩阵，用户升级指令「查清到底卡在哪」）

> 口径：真机 FMR0224116011480（WiFi 5GHz 协商 890Mbps），Mac 出口本机（Rust 42651
> 插桩版 / 现役 Go 41641 只读），测速 = App 内 4 流×10s+2s 预热（下行 = role=recv
> 窗口聚合）。全部同小时段跑（同 WiFi/同温区）。观测面 = 本批归因插桩

### 9.1 层 0 —— 裸局域网天花板（无 VPN）

手机浏览器直连 Mac `python3 -m http.server` 拉 1GB（6 轮）：
**74-107MB/s，中位 ≈94MB/s（752Mbps）**；WiFi 协商速率 890Mbps（hidumper WifiDevice
linkSpeed，freq 5220）。⇒ **局域网/WiFi 不是瓶颈**——对每个 VPN 组合留 ≥2× 余量。

### 9.2 层 1 —— 2×2 真机矩阵（同小时，MB/s 下行聚合 + 手机 CPU）

| 出口 \ 手机核 | Rust 核（smoltcp 栈 B） | Go 核（gVisor wgnet） |
|---|---|---|
| **Go 出口**（现役 41641） | **A：45.5 / 45.3**（CPU ~90%，单核） | **C：17**（CPU 274-384%，3-4 核） |
| **Rust 出口**（本地 42651） | **B：中位 33**（16.6-39 波动；**冷连轮 22.9-25.9**；CPU ~100-115%，单核） | **D：8.4**（×3 轮一致；CPU 138-307%） |

判读（两轴各自配对）：
- **手机核轴**：Rust 核两列全胜（45 vs 17；33 vs 8.4）——Rust 核是**更快**的接收端，
  Go 核烧 3-4 核只换来一半吞吐。**「手机核差异」不构成 Rust 侧缺口，反而是优势。**
- **出口轴**：Go 出口两行全胜（45.5 vs 33；17 vs 8.4）——**残余缺口在 Rust 出口的
  发送形态**：对 Rust 核 0.73×（中位），对 Go 核 0.49×（突发形态对 gVisor 接收端
  有敌意）。
- **R8-1 的 0.36× 是测量形态 artifact 为主**：那轮 Rust 出口测在刚建隧道后
  （WiFi 电源态未热），撞上「同步悬崖」（见 9.4）。同口径热态轮 B=0.73×，
  **0.5× 门在热态口径下通过**（冷态 22.9/45.3=0.51 贴线）。

### 9.3 层 2 —— Mac 出口侧分解（下行 bulk 期间）

| 项 | 实测 | 结论 |
|---|---|---|
| 出口进程 CPU（两实现） | **全部 0.0%**（14 样本 ×2） | **exit 侧不是 CPU 瓶颈**；R8-1「78% sendto」是线程内占比非核占满——syscall/encap/smoltcp 每包成本在此速率下离饱和差两个量级 |
| 发送批形态 | 均批 36-442 包/调用，**单调用最大 2379 包（≈3.1MB）**；均包长 1191-1308B（满 MTU，无小包问题） | 批化/唤醒粒度健康；**残余变量 = 突发形态**（smoltcp 单 poll 排空 min(cwnd,txq)） |
| tx_dropped（EAGAIN/失败） | 全部轮次 **0** | 非阻塞 socket + 4MB SNDBUF 下无 sendto 丢弃——8b 期担忧的 EAGAIN 丢弃面实测不存在 |
| CC 算法消融（HOMEWAY_CC=reno） | 冷连 25.9 vs cubic 22.9；热态同带（33-39） | **CC 算法非差异点**（缺口不因换 Reno 消失/收窄） |

### 9.4 层 3 —— 手机侧分解

- **Rust 核**：下行 bulk 单核 ~90-115%。A 轮（45.3MB/s）90% 未饱和 ⇒ 45MB/s 附近
  不是 Rust 核的硬顶；热态 B 轮 ~100-115%（突发消化更费——见悬崖机制）。
- **Go 核**：3-4 核（274-384%）才跑 17MB/s——手机侧最重的组合。
- **内核 UDP 缓冲**：B/C 轮 RcvbufErrors 增量 3-531（≈0）——内核收缓冲（4MB 请求）
  不丢；**D 轮的塌陷在 Go 核进程内部**（同突发敌意、不同缓冲点），非内核。
- **Rust 栈 B 收队列（QUEUE_CAP=1024）**：插桩核（f7d81934）热态轮 **0 溢出**
  （「栈B 收队列溢出」行未出现）——8b 期假设的「手机队列溢出丢包」在热态被证伪。

### 9.5 悬崖机制（冷连轮 22.9-25.9 的成因）

四流的逐秒序列在 t≈2-3s **同步塌落**（例：9.4→3.8→0.7 MB/s）后发散恢复——单流可
恢复到 17-19MB/s（路径容量证据）。发生条件 = 建隧道后 1 分钟内开跑（WiFi 电源态冷）
+ Rust 出口大突发；热态轮无悬崖且平坦（8.6-9.9MB/s/流）。Go 出口冷连轮（A=45.5，
force-stop 后 15s 开跑）无此形态 ⇒ **突发×冷电源态的交互**：出口单拍倾泻的
200-2379 包在接收端/空中接口上成团丢失，CUBIC/Reno 窗坍塌后按各自恢复律爬回
（恢复发散 = 轮间 16.6-39 波动的来源）。

### 9.7 修复路径（按归因排序，含量化预期——**归因已完成，本批未动优化**）

1. **出口发送整形**（第一优先）：拦截面 = 拦截栈单 poll 排空 → 驱动线程发送预算
   （把一次倾泻的 ≤2379 包切成有界的块（如 ≤128-256 包）随 poll 拍间隔投放——
   不是 sleep 步进，是「预算 + 下拍续传」）。预期：热态 B 中位 33→**~45**（Go 平价）；
   冷连悬崖消除（22.9→33+）；D 轮 8.4→**C 轮量级**（gVisor 接收端兼容性）。佐证：
   旧 CC 垫片（带 pacing）在 harness B 浅队列臂 8.1MB/s vs 现行 CUBIC 3.2——
   pacing/整形对塌陷形态有 2.5× 收益的历史同款证据（8f 对照跑）。
2. **上行同款审查**（次优先）：上行已 109-279Mbps 贴线过门，非缺口；整形落地后复测。

### 9.10 D-2 8n：第二瓶颈的数据链归因与两层机制修复（2026-10-06 凌晨；插桩 = 8n① commit d8a13be + aeff88a）

> 方法：双侧插桩——出口「tcp 观测」行（单流 段数/ACK 密度/通告窗 u16/在途估算/dup，
> on_plain+on_tx 累计 + cc 行 5s 窗差分）+ 手机核「热路径1s」行（收包率/均包长 +
> drain〔recv syscall + boringtun decap〕/poll〔smoltcp〕/encap〔ACK encap+sendto〕三段
> 分段耗时）。真机 FMR0224116011480，本地 Rust exit 42657（B 臂）/ 本地 Go exit 42643
> （A 臂），同小时段冷/热分离。

**基线复测（热态，B=整形 on 64MiB/s/160KiB〔R8-3 默认〕）**：

| 相位 | 手机收 | 手机核三段耗时/秒 | 出口侧 |
|---|---|---|---|
| B 下行 | **17.5MB/s**（12.6-22.4 均包 1255B） | drain 350-410ms + poll 20ms + encap 60ms | 滞留常驻 543-1280 包/0.7-1.3MB；ACK 密度 18 段/个；dup 90-211/5s；通告窗 u16 13-32K；在途 ≈400KB |
| B 上行 | 57-59MB/s | encap **800ms**（47000 包/秒逐包 encap+sendto） | 收 ACK 小包 1700/s（均 40B） |
| A 下行（同刻） | **41-46MB/s** | drain 430-570ms + poll 25ms + encap 50ms（top 107-129%） | （Go 出口无插桩） |
| A 上行（同刻） | 54-57MB/s | — | — |

**归因链（三方数据吻合）**：

1. **手机核 CPU 不是 B 的瓶颈**：B 臂 top 118-125% 但三段热路径仅占 ~480ms/秒
   （52% 空闲）；A 臂同 CPU（107-129%）扛 41-46。每字节成本差（R8-3 的 1.8×）
   的主因不是处理费而是**包到达率被出口压低**（B 12600-18000 包/s vs A
   35000-39000 包/s——同核同代码，处理能力证明在 A）。
2. **第一层：整形 R=64MiB/s 的桶限速注入排队延迟**。滞留队列常驻 ~500KB ⇒
   排队延迟 ≈ 深度/R ≈ 8ms ⇒ B 的 TCP RTT 17-27ms（WG rtt 同量级；A 同刻 6ms）
   ⇒ 吞吐 = 窗/RTT：B 400KB/23ms ≈ 17.4 vs A 270KB/6ms ≈ 45。**数学自洽**。
3. **第二层：burst 的「桶容量」语义让额度单拍倾泻**。R 修到 200 后滞留=0（排队
   消除、RTT 恢复）但 burst 2MB 的累积额度在 ACK 团到达后整拍倾泻 1-2MB 团块 ⇒
   空口成组丢失（终验 dup 260-657/5s）⇒ CUBIC 反复砍窗 ⇒ B 波动 19-40。

**梯度消融（同机同小时，出口 env 覆盖）**：

| 参数（R/burst） | 下行稳态 | 形态 |
|---|---|---|
| 64MiB/s / 160KB（桶） | 17.5 | 平稳；RTT 17-27（排队 ~8ms） |
| 128 / 256KB（桶） | ~14 | 锯齿（拍频×ACK 团耦合） |
| 160 / 512KB（桶） | ~15 | 锯齿 |
| 200 / 2048KB（桶） | 19-40 | 波动大（dup 团块丢 + 砍窗循环） |
| **200 / 256KB（单拍上界）** | **25-28** | **平稳无锯齿；滞留恒 0** |
| 200 / 128KB（单拍上界） | ~16 | 平稳（更平滑但吞吐回落——空口交织窗口利用降） |

**修复实装（8n②③ commit bf61e51；机制口径按评审 r1-1.1 认账修订）**：
`TX_SHAPE_RATE` 64→200MiB/s（R 的职责修正 = 团块钳制而非速率限制——路径容量由
栈内 CUBIC 自管；R 取 ~2× 层 0 天花板）；`TX_SHAPE_BURST` 2048→256KiB——**桶容量
= 单拍放行上界（同值）**：单拍释放 ≤ burst 的不变量由 credit 逐包扣减自带
（每拍开始 credit ≤ burst、放一包减一笔），无需独立的每拍计数；B4 轮的行为变化
完全来自 burst 2048→256 本身（曾手写的 beat 计数与该不变量同值，属死逻辑，评审
指出后删除）。**调大 burst 同时放开累积额度与单拍倾泻**（2048KB 形态实测团块
1-2MB、dup 260-657/5s）。放行率口径：排空期（滞留非空 ⇒ poll 1ms 拍）峰值
≈256MB/s；稳态空闲拍 5ms 时首批上界 ≈51MB/s——均 ≫ 实测吞吐 ⇒ 无持续排队；
团块上界 256KB = 修复前 3.1MB 倾泻的 1/12 ≈ Go 出口自然发送团量级。

**验收判定（任务书两条口径）**：
- **≥40MB/s（Go 平价带）：未稳定达标**——定稿形态 B 热态 25-28 平稳（单轮
  30-40 曾现），A 同批 41-46；**B/A ≈ 0.6**。
- **完整数据链架构结论**：①手机核 CPU 非瓶颈（52% 空闲 + A 臂同核扛 45 的能力
  证明）；②出口排队延迟层已修（滞留 0、RTT 恢复——单拍上界下 RTT 回落至
  在途/吞吐自洽）；③出口倾泻层已修（团块 1/12、dup 显著降）；④**剩余缺口
  （25-28 vs 41-46）的物理归因** = 出口发送的**拍粒度与 ACK 时钟的交织**：Go
  出口 gVisor 的发送由对端窗+自身调度自然平滑（微秒级间隔），Rust 出口以 1ms
  拍 × ≤256KB 团发送（每团在空口 ~2.3ms 传输窗），团间空隙 + 空口交织窗口利用
  率低于连续流；128KB 单拍（更平滑）反而 16——**「平滑度↔窗口利用」的平衡点
  在当前拍频结构下 ~256KB**，再往下需要**逐包 pacing**（在 256KB 团内按
  ~10µs/包间隔释放——需出口发送循环从「批 sendto」改「按时戳散布」，改动面在
  驱动线程的 poll 节奏，属下一档工程）。次因：手机 smoltcp 接收端每 poll 一拍
  只回一个累积 ACK（观测 18 段/ACK），CUBIC 爬窗慢于 Go 出口侧的每 2 段 ACK
  节奏——同因归 §9.7 路径③（手机侧每字节成本的下一档）。
- **上行不受影响**（57-59MB/s 恒定——上行瓶颈在手机核 encap 800ms/秒的逐包
  encap+sendto，与出口整形无关；sendmmsg 批化在 8b 期实测劣化已移除，OHOS
  批量路径的机制归因仍开放）。
- **冷连**：定稿形态平滑爬坡无「同步塌死」（R8-3 修复前的 9.4→3.8→0.7 形态
  不再现）；冷/热比 0.70 门的终测建议同批冷热交替多轮中位（本批冷连轮恰逢
  环境低带，单轮比值不可用——R8-2 教训「单轮数据不可用于 A/B」）。

**8r 的两个实测教训（机制面，入册）**：

- **增益 2.0 档整体不 engage**：稳态 produce 率 = ACK 时钟 ≈ est ≪ 2×est ⇒

- **组合形态的常驻整形滞留**：8s 的密 ACK 时钟让出口 CUBIC 窗快速长大（txq 满
  1MB×4 流），窗过冲（≫ BDP）改停 pacing 队列——**整形滞留 2325-2766 包/

  面向无 8s 的接收端路径（旧核手机、经 TUN 的应用流量——OHOS 内核 ACK 时钟不受
  8s 覆盖，**该路径本批未测**）与快路径。
- 插桩副产：五元组复用的 ACK 序号回绕可产生 +378MB 单跳假推进（est 顶到 3.6G）
  ——已加单段 1MiB 截断（真 ACK 推进 ≤ 通告窗）。

**harness 三臂（反过拟合约束 2，`pacing_three_path_arms`，负载机串行）**：
慢路径（2.5MB/s/40ms/64KB 队列）on/off = 0.8/0.5（pacing on 更优，队丢 110→113、
吞吐 +60%）；快路径（120MB/s/2ms/8MB 队列）on/off = 6.8/8.5（0.8×，≥0.7 门——
负载机泵粒度 630/s 的排空上限，真机 pselect 20k/s 无此约束）；冷空口 on/off
分离保持（on 5.0/0 到达丢失 vs off 3.8/129）。**调参梯度在三臂同时过门。**

## 10. 已知限制（反过拟合约束 3；2026-10-06 D-3 起）

- **性能验证覆盖形态**：家宽上行 + 局域 WiFi 5GHz（协商 510-890Mbps）实测；
  **服务器/有线（≥1Gbps）、蜂窝、2.4GHz 形态未做真机性能调优**——功能性由
  matrix/互操作矩阵覆盖，性能面以 harness 三臂（慢 2.5MB/s/40ms、深 24MB/s/
  26ms、快 120MB/s/2ms）为准。快路径（2.5G+）用户建议出口 config
  `[serve.tx_shape]` `pacing = "adaptive"`（自适应 est 无人为上限）。
- **pacing=adaptive 显式开启的尾延迟**：8s 在位的接收端上 pacing 无增益且 CUBIC
  窗过冲会改停整形 FIFO（实测 2-4MB 常驻，队尾排队 ≈ 队深/pace ≈ 100-150ms）；
  建议 pacing 只用于无 8s 的接收端路径（旧核手机/经 TUN 的应用流量/快路径）。
- **日间/夜间带差异**：同一物理环境下 A 臂（Go 出口）日间 26-33 vs 夜间 41-46
  （空口竞争）——绝对吞吐数字必须带时段口径引用；夜间带复测是 D-3 的登记后续。
- **8s 适用域**：只覆盖核心自连（speedtest/files/term/探测 = smoltcp 收端）；
  经 TUN 的应用流量由 OHOS 内核回 ACK（自带密时钟），8s 对其零作用、8r（显式
  开）是唯一覆盖线——该路径的定量收益未测（登记）。
