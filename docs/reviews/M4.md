## 6. 偏离设计 + 原因（逐条，均已在 commit message 登记）

1. **`pump.rs` 的 `upstream`/`downstream` 返回类型由 `u64` 改为 `CopyEnd{bytes, err}`**
   （设计 §2.4 只写「泛型化 ≈4 行」）。原因：§3.3 要求的「目标侧中断」additive 行需要**结束原因**；
   socketpair 腿不读 `err` ⇒ 行为逐字保留（泵半关用例全绿）。
2. **`pump_dial` 的目标侧中断行逐方向落**（不是 `join!` 之后统一落）。原因：本机实测——
   「客户端长时间不再发数据」会让另一方向长期不返回 ⇒ 统一落行时该行 >8s 不出
   （首版实现即此形态，被用例抓到）。落点仍在 `dial.rs`，不动 `pump.rs` 的语义。
3. **`crates/homeway-core/tests/quic_pf_e2e.rs` 提前落地（S5 的面）**：本棒的收口要求包含
   「portfwd 本地端到端 + 阀/FlowGuard/计数逐字保留断言 + 泄漏判据」，而 A8/回执/RAII 的**真面**
   只能在真世代上读。故落**两条最小用例**作为 S5 的起点；S5 仍需补：`tools/quic-pf-e2e.sh` 驱动、
   **四形态 × 三失败**归因表、spec R1–R5 本机面（含 R1 的三条结构性 SHALL 的 grep 断言）、真机四场景。
4. **`0x26` 的真 socket 判据缺席（如实登记）**：本机无 hermetic 黑洞（设计 §12.1 自己记了
   `169.254.169.254` 的 1.5s `TimedOut` 是**本机现象**）⇒ 该码只有**注入 future** 的单测证据。
   **S5 的可操作钩子**：`tools/quic-wedge-proxy.py`（ladder e2e 已用它造黑障）挡在出口与目标之间
   ⇒ 可造真超期（客户端预算 > 出口 10s 时由出口给 `0x26`）。
5. **A8 判定顺序 = 地址类先于端口 0**（设计未指定）。理由：`0.0.0.0:0` 报地址类信息量更大；
   `127.0.0.1:0`（`targetPort=0` 旁路的线上形态）仍报端口 0——两行都在单测里钉住。
6. **泄漏判据 N = 80**（设计写 63）：pf 失败行节流「首 5 + 每 20」⇒ 63 不可见（§2.4 已说明）。
7. **`remain()` 对「预算大到 `Instant` 装不下」的处理**：视为无截止但每步 RPC 仍用 1h 有界等待额
   （`dial_ms` 是配置面，`Instant + Duration` 会 panic）——纯防御，正常配置不可达。

## 7. S1–S3 交下的两条待确认 —— 结论

① **出口「目标侧中断」行不节流**：**维持不节流**。理由：该行**每流至多 2 行**（上/下行方向各一），
流数本身受岛内 bidi 额度（62/连接）构造性约束 ⇒ 无刷屏风险；节流会抹掉「目标反复自杀」的证据。
（`exit/dial.rs` 的注释已写；单测 `service_stream_dial_target_reset_logs_the_additive_line` 钉住末条。）

② **出口 dial 腿 `TCP_NODELAY`**：**实测后改齐**。取证：WG 档出口的 transit 腿在拨号完成后设
`TCP_NODELAY`（Go `SetDelayOption(false)` 同口径，`server/intercept/mod.rs:2233-2246`），dial 腿原先**未设**
⇒ 同一映射在两条承载下的小包时延语义有差异。处置：`exit/dial.rs` 在拨号成功后补 `let _ = tcp.set_nodelay(true);`
（与 intercept 同形：最佳努力、失败不致命），commit message 记「实施期对齐」。**影响面**：仅本机/真机的
小包时延（握手/回执/泵路径不变）；探针与字节判据零影响（本棒全门复跑见 §8）。

## 9. 偏离与原因（逐条）

1. **设计 §9-⑥ 的措辞「浏览器立刻『连接被重置』」与真机形态不同**：真机浏览器（`com.huawei.hmos.browser`）
   对「对端立刻 RST」渲染的是自有错误页 `网站暂无响应，请点击屏幕重试`（含其自检三态图标）。
   核侧真值是**立刻失败**（7ms 出 `拨号失败 #1`，非挂起）⇒ 差异只在浏览器文案层，**如实登记**不追改文案。
2. **R3-S② 的「未连接时进页面」在 tier 侧被门控**：点「端口转发」入口在未连接时提示需先连接 ⇒
   该 scenario 的「页面内显示未连接」形态本轮**不可达**（门控本身是更强的行为：不给陈旧态）。
   页面内 `!live ⇒ 未连接` 的渲染支路在代码面（`PortForwardsPage.ets:225-228`）但未取真机读数 ⇒ 登记。
3. **出口行节流是判据的一部分**：`log_due(n)=n≤3 ∨ n%100=0`（全局计数，Q-F-B 既有语义）⇒ 断言出口行的
   用例必须落在**新起出口**的头三次额度内。`tools/quic-pf-e2e.sh` 的**顺序**（ride → 0x26 → forms → leak → s4）
   即为此固定；手工单跑前须先 `wipe`+`start`（用例 doc 已写）。
4. **真机包 = `82a29c7`（不含 §7-② 的 `TCP_NODELAY` 对齐）**：该对齐发生在真机跑完之后，只影响小包时延、
   不影响任何真机观察项（往返/状态/级联删除/归因面）⇒ 不重跑真机；**如实登记版本差异**。
5. **S4 与 S5 的 e2e 用例合批一个 commit**（`82a29c7`）：同一测试文件、同一台架、同一次运行
   （S4 的 falsify 读数只能在 e2e 里采）⇒ 拆开会产生「不可自证的中间态」。
6. **`0x26` 的真面用「本机黑洞地址」而非楔子代理**：`tools/quic-wedge-proxy.py` 是 **UDP** 代理
   （挡在客户端↔出口的 QUIC 路径上），而 `0x26` 由**出口的 TCP 拨号**产生 ⇒ 楔子不可能造出该码；
   改用设计 §12.1-④ 指定的黑洞目标 `169.254.169.254:80`（本棒复测仍为黑洞：>4s 无应答）。
