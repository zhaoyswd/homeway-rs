# P2 技术批设计与评审记录（内层 MTU 上调）

> P2 批（2026-10-07 起）。任务书 = 性能优化 P2「内层 MTU 上调」：现 TUN/隧道内层
> MTU 1280 按最坏外层路径保守设定；外层 1500 时内层可到 1380–1400，包数直降 ~8%，
> 每包固定开销（encap/sendto/唤醒/TUN 写）等比减少。P1 终验（PERF-AB §9.13）结论
> 「发送线程机制生效但吞吐不动」⇒ 每包开销占比权重上调，P2 确定性收益预期提高。
> **坑 4/23 防回归是第一设计约束**：当年内层 MTU + 隧道开销 > 外层路径承载 →
> 丢包/分片黑洞。本文件 = P2a 设计（§一）+ 评审（§二起追加）。

## §一 P2a 设计（拍板稿）

### 1.1 坑 4/23 历史根因（防回归的对象）

- **坑 4**：MTU 必须在隧道自身承载能力之内（tier `docs/agents/pitfalls.md` #4）。
- **坑 23**：TUN MTU 1360 → 大包超隧道承载上限 → 隧道内被丢 → TCP 反复重传 →
  「能连、DNS/TLS 都通、首页白屏/爬行」（蜂窝+中继最明显；实测 1360 回程 3 分钟
  ~140KB，1280 正常渲染整页）。
- **形态学本质**（跨栈不变）：`内层包长 + 封装开销 > 外层路径可承载` → 要么分片
  （多数路径可达但降速、丢失放大），要么黑洞（分片被丢/被中间盒拒收）。当年栈
  （tailcat/Tailscale）的「隧道自身 1280 硬上限」在现栈（homeway-rs = boringtun
  自管 UDP）不再存在——**现栈的真实约束 = 外层路径 MTU − WG 封装开销**：
  - v4 外层：20(IP) + 8(UDP) + 4(类型/保留/接收方) + 8(计数器) + 16(poly1305) = **60B**；
  - v6 外层：40 + 8 + 4 + 8 + 16 = **80B**。
  - 外层 1500 ⇒ 内层上限 v4=1440 / v6=1420；外层 1492（PPPoE）⇒ v6 口径 1412。
- **防回归总纲**：任何上调必须带「外层路径余量确认」前置；宁可不升。确认机制
  分层见 §1.4。

### 1.3 候选形态与拍板

| 形态 | 内容 | 判定 |
|---|---|---|
| a) 纯配置门控 | config 键 + 手动开（仅已知 ≥1500 路径） | 余量确认完全靠人——满足硬规则字面，但「确认」无机器面 |
| b) DF 探测式 PMTU 发现 | 出口路径发 DF 探针，确认 ≥1500 才升 | 机制最强，但完整 PMTUD（周期重探/漫游重探/ICMP 学习）超出本批 |
| c) 双档默认 | 1280 默认 + 1380 opt-in | 默认零变化，与 a 天然复合 |

**拍板 = c 双档 + a 配置门控 + b 的两件轻量护栏**（三者不互斥，取最小复合）：

1. **双档**：`1280`（默认，字节级零变化）与 `1380`（opt-in）。1380 取值依据：
   - v6 外层最保守口径 1380+80=1460 ≤ 1492（PPPoE）≤ 1500，**对 v4/v6 外层、
     以太/PPPoE 均有 ≥32B 余量**；
   - 包数收益 1240→1340（+8.06% 载荷/包，包数 −7.5%）= 任务书预期 ~8%；
   - 不取 1400+（v6+PPPoE 双重叠加时余量 <12B）；不取 1420（v6 以太零余量）。
   代码面常量域 = `[1280, 1420]` clamp（1420 = 1500−80 绝对上限），本批只开放
   1280/1380 两档（App/出口配置校验层限制），clamp 是防呆不是功能。
2. **两端独立配置，靠 TCP MSS 协商自洽**（无 wire 协议变更）：
   - 手机：`aa start … --ps tun_mtu 1380` 注入 → ConfigManager(GSKV) `tunMtu` →
     prepare cfg.mtu=1380（请求值）；
   - 出口：config `[serve] inner_mtu` / flag `--inner-mtu` / env `HOMEWAY_INNER_MTU`
     （env > config > 默认，对齐 tx_shape 消融缝惯例）→ 拦截栈 caps；
   - **收益需要两端都升**（effective_mss=min(本端, 对端通告)，单端升=协商回旧值，
     无收益、无害）；两端不一致窗口详见 §1.6。
3. **升档前置门（手机核内，每世代一次）**：`cfg.mtu > 1280` 时核在 status 组装前
   判定 `mtuEff`：
   - `link.via ≠ direct` → **不升**（坑 23 的历史形态就是中继腿；直连确立后才可能升）；
   - **DF 探针**：独立 UDP socket（族别跟随采纳端点）、设 DF（Linux/OHOS
     `IP_MTU_DISCOVER=IP_PMTUDISC_DO` / `IPV6_MTU_DISCOVER`；macOS `IP_DONTFRAG` /
     `IPV6_DONTFRAG`）、`send_to(采纳端点, inner+32 字节载荷)`——
     - `EMSGSIZE`（本地路由缓存即拒）→ **不升**：手机本地段 MTU < inner+60/80；
     - 成功发出 → 升（载荷长度 = 内层满包的外层 IP 总长减 20/40−8，探针与真实
       WG 满包同尺寸；发到出口 WG 端口，出口按坏包静默丢，无害）；
     - 其它错误（网络不可达等）→ 保守**不升** + 记行。
   - 判据行：`mtu: 档位 1380（直连+DF 探针通过）` / `mtu: 维持 1280（原因）`。
   - **盲区如实登记**：探针 verdict 是本地路由口径，下游瓶颈（蜂窝真 PMTU <
     接口 MTU）探针不可见——由 §1.4-2 出口侧护栏 + 无 DF 分片可达兜底 + 配置
     文档「仅已知 ≥1500 路径开」收口。
   - status 载荷新增**扁平键 `mtuEff`**（恒出，数值；1280/1380）——扩展建
     VpnConfig 时用它（prepare 发请求值、status 回生效值）。
4. **出口侧两道护栏**：
   - **启动自检（确定性、可移植）**：opt-in>1280 时出口读出向接口 MTU
     （getifaddrs 面向默认路由接口；绑卡形态=所钉卡），`inner+80 > iface_mtu` →
     拒绝升档、回落 1280 + 判据行（`intercept: 内层 MTU 拒升（出口接口 MTU=N）`）；
   - **运行时 DF+EMSGSIZE 降档（best-effort）**：opt-in 档主 WG socket 尽力设 DF
     （双栈 socket 对 v4/v6 两族都设，失败仅记一行、不阻断——macOS 对 v4-mapped
     的 IP 级选项作用面不可移植，登记为已知限制）；发送面观测到 `EMSGSIZE` →
     拦截栈 caps 降 1280（**只降不升**，进程生命周期内；smoltcp dispatch 重读
     caps ⇒ 存量+新增流后续段立即变小）+ 判据行。DF 若未生效 ⇒ 行为=现状分片
     可达（降级但不黑洞），不劣于不开。

### 1.4 外层余量确认的分层（坑 4 防线总表）

| 层 | 机制 | 覆盖 | 残余 |
|---|---|---|---|
| L0 | 默认 1280 不变 | 全部用户 | 无 |
| L1 | opt-in 配置（文档：仅已知 ≥1500 路径） | 误开蜂窝等 | 人误判 |
| L2 | 手机 via=direct 门 | 中继腿（坑 23 历史形态） | — |
| L3 | 手机 DF 探针（本地段） | 手机本地段 MTU 不足 | 下游瓶颈不可见 |
| L4 | 出口启动接口自检 | 出口侧接口 MTU 不足（可注入测试） | 路径中段 |
| L5 | 出口运行时 DF/EMSGSIZE 降档 | 下行路径 PMTU 退化 | DF 不生效平台=分片可达兜底 |
| 兜底 | 外层 socket 默认无 DF ⇒ IPv4 分片可达 | 分片敌视网络外的全部形态 | 稀有分片黑洞（登记） |

**结论**：升 1380 需同时穿过 L1–L3（手机）与 L1/L4 或 L5（出口）；任何一层拒绝
即回落 1280。与坑 23 事故形态（中继+分片丢）对照：L2 直接挡中继；分片丢形态由
L3/L4/L5 + 兜底层把「静默黑洞」变成「回落 1280 或分片可达」。

### 1.5 MTU 变更的运行时切换语义（评审必答 ②）

- **手机侧：TUN MTU 是 VpnConfig 属性，接口建立时固定，OS 不支持在跑中改** ⇒
  变更 = 重建接口。本批的时序天然规避「跑中变更」：升档判定发生在**建链后、
  建 TUN 前**（现状序：warmup ready → 扩展读 status（拿 exitIp 建 DNS + mtuEff）
  → createVpnConnection → attach），mtuEff 是**每世代一次**的先验值，接口建立
  时即终值。**漫游/换网后不自动降档重建**（重建链路 markUnhealthy 面留作 P3
  候选，登记 ROADMAP）；期间的形态 = 上行外层分片可达（不黑洞）。
- **出口侧**：config 起一次；EMSGSIZE 运行时**只降不升**（重升=重启出口）。
- **两端不一致窗口**：见 §1.6。

### 1.6 两端不一致窗口的兼容（评审必答 ③）

- **TCP（全部业务面：过境流/栈 B 自连）**：MSS 协商自洽——`effective_mss =
  min(本端 caps 推导, 对端 SYN 通告)`，两侧发送段永不超过对端接收口径；
  单端升档 = 该端无收益（被对端 1240 压回）、无双洞；先后升级任意顺序安全。
- **UDP 过境**：无 MSS 语义；出口下行内层 UDP 包理论上可达 64KB——**现状已
  如此**（互联网大 UDP 数据报 >1252B 时内层包已可超 1280，出口照发、手机本地
  交付容忍），升档只减不增该面，无新风险。
- **WG 层**：内外层长度无协商假设（读缓冲 65535/65536+148 与 MTU 解耦）。

### 1.8 测试计划（P2c）

1. **单测**（homeway-rs）：clamp 域；TunDevice caps 默认/with_mtu；升档门
   （via=relay 拒、探针失败拒、直连+探针过=升）；status mtuEff 键存在性；
   DirLink mtu_limit 丢包计数；出口启动自检（注入接口 MTU）；EMSGSIZE 注入降档。
2. **harness 三臂消融**（`--ignored` 性能测试，慢 2.5MB/s/40ms、深 24MB/s/26ms、
   快 120MB/s/2ms）：内层 1280 vs 1380 两臂 × 三链路，门 = 1380 臂不劣化 +
   包数差登记（段尺寸 1240→1340 的机器验证）。
3. **坑 4 回归专测（harness 注入）**：内层 1380 + DirLink mtu_limit=1340
   （模拟外层 1400−60）：门开形态 = 数据段全丢（复现坑 4 形态学）→ 证明注入
   有效；**带门形态** = 探针/自检拒升 → 1280 全通（正确降级、零分片黑洞）。
4. **真机 2×2**（FMR0224116011480 × 本地 Rust exit）：MTU 1280 vs 1380 臂同刻
   交错（§9.13 口径：force-stop→注入→开关→60s 热态；speedtest + TUN 600MB 下载）；
   判据：speedtest/TUN 中位增益 + 判据行 `mtu: 档位 1380` + stats 行包数对表。
5. **坑 4 回归专测（真机形态，若可注入）**：Mac 出口接口 MTU 降至 1400
   （需 sudo；不可用则 harness 注入为准）→ 出口启动自检拒升 → 判据行 + 全通。

### 1.9 反过拟合三约束延续（PERF-AB §10 口径）

- 默认档字节级零变化（未注入/未配置时全部路径走旧值）；
- harness 三臂（慢/中/快）不以单一环境调参；
- 真机数据带时段口径、层 0 锚同刻、臂交错、中位对读。

## §二 技术设计评审（设计门，2026-10-07；对象 = §一 全节）

> 评审方式：设计稿通读 + 关键源逐行核对（核侧 stackb/wgcore/intercept/bind/
> wtransport/tun_exec/udpdbatch/status/e2e 文档 + smoltcp 0.14 源码 + tier 侧
> TierVpnExtensionAbility/TierConfig/NapiPayload/EntryAbility/HealPolicy + 两道
> 对账脚本）。**结论 = 拍板形态（双档 + 门控 + 双护栏）成立，但设计稿有 4 处
> 高危项必须先整改再进 P2b**：① L5 运行时降档在 smoltcp 0.14 上是空操作（caps
> 构造期快照）；② 手机核自己的 stack B 走的是未门控的 cfg.mtu（L2 门只保护
> VpnConfig 那条路）；③ status 新键 mtuEff 撞两道既有门（Go 向量逐字节对账 +
> tier/ledger 并集对账 + baseline sha 锚定）；④ "无 DF 分片可达"兜底只对 IPv4
> 成立，而 1380 的取值论证建立在 v6 最坏口径上。

### 2.1 必答三题结论

**① 分层防线有漏 —— 漏 3 处（2 高 1 中）。**

- **L2 有实装漏洞（高）**：§1.7-2 的 `CoreConfig.mtu ← facade 传 cfg.mtu`（请求值）
  与 §1.3-3 的门（status 组装前判定 mtuEff）不是同一条数据流。手机核的
  `StackB::new` 在 `Client::start` 内（`wgcore/mod.rs:1109`）**早于建链**，
  拿不到 `via` ⇒ stack B 的 caps 恒 = 请求值（1380），**L2/L3 门一概不适用**。
  relay 形态下 speedtest/files/term 自连仍按 1380 发 1340 段 = 坑 23 形态学在
  栈 B 路径原样复现（外层 v6+中继封账见 2.2-①）。
- **兜底层只覆盖 IPv4（高）**：兜底行自己写的是「IPv4 分片可达」（§1.4 表末行）
  ——v6 路由器按 RFC 8200 不分片，只有源端分片，而源端要先知道更小 PMTU。
  1380 的取值论证（§1.1「v6 外层最保守口径」/§1.3-1）恰是 v6 口径 ⇒ **取值
  最保守的那一族没有兜底**。且手机侧无第二道观测：`send_wg` 把 EMSGSIZE 当普通
  本地错误吞掉（`wtransport/bind.rs:274-285`），既不降档也不留世代标记，只刷新
  `last_local_send_err`（该位是"环境噪声"判据源，见 2.2-⑧）。
- **L5 为空操作（高，见 2.2-③）** ⇒ 出口侧实际只剩 L4 一次静态自检。
- L3 探针的盲区登记（§1.3-3）本身诚实 ✓，但"由 §1.4-2 出口侧护栏 + 无 DF 分片
  可达兜底 + 文档收口"三件套里，第一件 inert、第二件 v4-only ⇒ **论证不成立，
  需补一条确定性替代**（建议见 2.2-②：外层族=v4 才允许升档 + 手机侧 EMSGSIZE
  判别，两件都便宜且确定）。

**② 运行时切换语义：时序论证"字面错、实质成立"；漫游风险评估不完全可接受。**

- 实际序（tier 逐行核）= prepareTunCore（250ms 轮询只消费 state/meowed/readyBy，
  `TierVpnExtensionAbility.ets:863-874`）→ `createVpnConnection`（:685，**对象
  工厂，不建接口**）→ `buildVpnConfig()` 内 `readTunStatus()`（:2161/:2224，
  拿 tunIp/exitIp，空即硬失败）→ `connection.create(config)`（:690，**接口在此
  定型**）→ attach（:710）。设计稿「读 status → createVpnConnection → attach」
  把顺序写反了，但**关键约束（读 status 在建接口之前）成立** ⇒ mtuEff 放
  buildVpnConfig 与 exitIp 并列可行 ✓，每世代一次 ✓。
- 「VpnConfig 建立后固定」：tier 侧无 update/setMtu 调用、buildVpnConfig 每世代
  只跑一次（:687）✓；但 OHOS SDK .d.ts 本机不在（无独立证据）⇒ 建议补 SDK 依据
  一句（低）。
- 漫游：(a) **快路径** `tryRebind`（:1227/:1368）就地重绑、不重建接口、不重读
  mtuEff ⇒ 换到更差网络维持 1380 —— 设计承认，但兜底论证仅 v4（同①）；
  (b) **慢路径** `rebuildTunnel`（:1408-1431）本来就会 destroy + 重跑
  `buildVpnConfig` ⇒ **会隐式重读 mtuEff（可能升也可能降）**——设计稿「漫游后
  不自动降档重建」与现状树不符，应改写为「快路径不降档；全量重建路径自动重读」。
- 出口侧「config 起一次 + 只降不升」语义 ✓（但降档本身 inert，见③）。

**③ 两端不一致窗口：TCP 面论证成立，UDP 面论证只对一半，另有一处表述错误。**

- **TCP 成立** ✓（smoltcp `tcp.rs:2631-2632`：`local_mss = cx.ip_mtu() − IP头 −
  TCP头`，`effective_mss = min(local_mss, self.remote_mss)`；`remote_mss` 只在
  SYN/SYN-ACK 落定（`tcp.rs:1908/1961`），此后**永不重读**；OHOS 内核同档按路由
  MTU 定 MSS）⇒ 单端升档：本端发送段 = min(新本端, 旧对端) = 旧值 = 无收益；
  永不超对端接收口径 = 无害；存量连接不受影响（升档对存量零收益也零风险）。
  通告窗与 `max_burst_size`（None）不引 MTU 依赖 ✓（`packet.rs:155-165` 只在
  Some 时截窗）。
- **表述错**：§1.2 表「每次 dispatch 重读」/§1.3-4「dispatch 重读 caps ⇒ 存量+
  新增流后续段立即变小」——重算的是 `min(构造期快照 caps, 已锁 remote_mss)`，
  设备 caps 运行时变更**不可见**（见 2.2-③）。
- **UDP 面**：「现状已如此，升档只减不增」只对**出口下行**成立（出口的 inner
  UDP 尺寸由远端决定、与 caps 无关）；**手机上行不成立**——内核按 TUN MTU 分片，
  1280→1380 使上行外层 +100B，"只减不增"在最大包长口径上是假的（包数减、单包增）。
- **新增风险（中-高）**：§1.3-4 出口主 socket 设 DF 后，今天靠 IPv4 分片送达的
  大 inner UDP（远端决定尺寸，caps 降档救不了）会变成 EMSGSIZE 本地丢 —— §1.6
  「无新风险」与 L5 自身矛盾（见 2.2-④）。

### 2.2 逐条问题（位置 / 问题 / 建议 / 严重程度）

1. **§1.1 + §1.3-1 + §1.3-4（P2.md:21-24/52-58/84-85）封装开销漏算腿帧** ——
   真源：腿帧 `[0xBB][kind]` = **2B**（`wtransport/frame.rs:54-59`；两端
   `send_wg`/`send_wire_inner` 恒加，`wtransport/bind.rs:270`、`server/bind.rs:832`），
   中继腿再加 `[0xAA][id8]` = **9B**（`wtransport/bind.rs:387-396`）。
   实测封账（inner=1380）：

   | 腿形 | 开销 | 外层总长 | 1500 余 | 1492 余 |
   |---|---|---|---|---|
   | 直连 v4 | 20+8+28+2 = 58 | 1438 | 62 | 54 |
   | 直连 v6 | 40+8+28+2 = 78 | 1458 | 42 | 34 |
   | 中继 v4 | +9 = 67 | 1447 | 53 | 45 |
   | 中继 v6 | +9 = 87 | 1467 | 33 | **25** |

   ⇒ 1380 仍安全 ✓，但「≥32B 余量」错（最坏 25B）；**clamp 上界 1420 错**：
   v6 中继 = 1507 > 1500（v6 直连 1498，仅 2B）。真实绝对上界（最坏组合
   v6+中继+PPPoE）= 1492−87 = **1405**。
   **建议**：§1.1 表与 L4 判据式（`inner+80` → `inner+87`）统一按 58/78/67/87
   重写；clamp 改 `[1280,1400]`（防呆口径取最坏组合留 5B）；§1.3-1 的
   「不取 1420」理由改为"中继 v6 越界"。**严重程度：中**（对已开放的 1380 无
   实害，是防呆域与论证口径错）。

2. **§1.4 兜底行 + §1.3-3 盲区收口（P2.md:100-107/77-79）** —— 见必答①。
   **建议**（确定性替代，按性价比排）：
   (a) 升档前沿加一条「采纳端点族 = v4」（外层族可从 `Snapshot.ep` 判，v4-mapped
   已被 `unmap_v4_in6` 归一，`udpbatch.rs:147-152`）——v6 外层不做升档，把
   "无兜底"那一族直接排除；代价是 v6-only 路径零收益（可后续批次再放开）；
   (b) 手机侧 `send_wg` 增 EMSGSIZE 判别：单列计数 + 判据行 + 世代降档标记
   （不要进 `last_local_send_err` 噪声位），至少让"黑洞"变成可诊断；接口重建
   仍可留 P3；
   (c) §1.4 兜底行改注「**IPv4 专用**；v6 外层无兜底，由 (a) 排除」。
   **严重程度：高**。

3. **§1.2 表 + §1.3-4 + §1.7-2/4（P2.md:35/89-90/136-137/141-142）smoltcp caps
   不可运行中变更** —— 真源：`InterfaceInner.caps` 只在 `Interface::new` 取一次
   （smoltcp `iface/interface/mod.rs:208` → `:129/:274`）；`poll` 不刷新；
   `socket_egress` 里 `let _caps = device.capabilities();`（`:717`）**丢弃**；
   全 API 无 setter；`ip_mtu()` 读的就是这份快照（`:858-859`）。⇒
   `TunDevice` 增 `mtu` 字段 + `capabilities()` 返字段，对**已建 Interface 完全
   无效**；L5「只降不升」= 空操作；§1.8-1 的「EMSGSIZE 注入降档」若只断言设备
   字段变化 = 重言式测试。**存量连接面核查（问题清单另问）**：`remote_mss` 落定
   后永不重读 ⇒ 降档若真生效，本端发送段立即 = min(新 local, 旧 remote) = 新值
   ✓（安全方向）；升档对存量零收益 ✓（无害）；通告窗与 MTU 无关 ✓，
   `max_burst_size=None` 不截窗 ✓；**入站无 MTU 门**（`ipv4.rs:95-146` 全无
   `ip_mtu` 引用）⇒ 降档不会把对端在旧 MSS 下发来的大段丢掉 ✓ —— 这条要在设计
   里写明（是本设计的利好，不是坑）。
   **建议**：L5 的"降 caps"改为**用新 caps 重建 Interface、复用同一 SocketSet**
   （重放 ip_addrs/routes；socket 状态独立于 Interface，`dispatch` 只查
   `cx.has_ip_addr`——`tcp.rs:2448`），或 `[patch.crates-io]` vendored smoltcp
   暴露 caps 刷新（本仓已有 ring 的 patch 先例）；两者都做不到就**删掉 L5**，
   §1.4 如实登记"出口侧仅 L4 一次静态自检"。**严重程度：高**。

4. **§1.3-4 出口 DF（P2.md:86-91）** —— (i) macOS 双栈 AF_INET6 + v4-mapped：
   `IP_DONTFRAG=28`（仅 apple）/`IPV6_DONTFRAG=62`（apple+linux）/
   `IP_MTU_DISCOVER=10`/`IP_PMTUDISC_DO=2`/`IPV6_MTU_DISCOVER=23`/
   `IPV6_PMTUDISC_DO=2` 常量都在（libc 0.2.190）；但 AF_INET6 上设 IPPROTO_IP
   级选项在 macOS 通常 ENOPROTOOPT（设计已认账）——**更好的确定性替代**：
   Linux/OHOS 优先设 `IPV6_DONTFRAG`（v6 级、AF_INET6 必可设、v4-mapped 亦走
   IPv6 入径），macOS 同理只设 `IPV6_DONTFRAG`，并以真路径实测确认 v4-mapped
   生效（做不到就退回 L4-only）。 (ii) **DF 生效 = 新丢包面**：出口的大 inner
   UDP（>路径 MTU−58）今天分片可达，DF 后本地 EMSGSIZE 即丢，且 caps 降档对
   UDP 无效（尺寸由远端定）⇒ §1.6「无新风险」需改写为"TCP 面有新护栏；UDP 面
   新增一类本地丢包（登记 + 计数）"。 (iii) L4 的 "getifaddrs 读向接口 MTU"
   **在 Linux/OHOS 不成立**（getifaddrs 的 `ifa_data` 是 link stats，无 MTU）——
   需分派：macOS = `ifaddrs`+`if_data.ifi_mtu`（libc apple `if_data`），
   Linux/OHOS = `ioctl(SIOCGIFMTU)`（libc `SIOCGIFMTU=0x8921` 在位），并给
   `egress::IfaceInfo`（`server/egress.rs:108-118`）加 `mtu` 字段。
   **建议**：按上改 (i)(ii)(iii)；§1.3-4 文字保留 best-effort 声明但删掉"DF 若
   未生效 ⇒ 不劣于不开"的结论（DF 生效才是新风险源，方向反了）。
   **严重程度：中-高**（(ii) 是行为回归，(iii) 是可移植性硬伤）。

7. **§1.7-2 ACK_DRAIN_BYTES 动态化的实现面（P2.md:137）** ——
   `ack_drain_bytes()` 是**进程级 OnceLock**（`wgcore/mod.rs:71-80`），只取首值；
   而 `Client::start`（每世代、甚至同世代 rebuild —— `tun_exec.rs:286/335`）都会
   新建 StackB ⇒ "2×生效 MTU"在多世代/多 MTU 下不成立。语义本身 ✓：smoltcp
   立即 ACK 判据 `remote_last_ack + remote_mss < remote_seq_no + rx_buffer.len()`
   （`tcp.rs:2403`，严格 `<`）⇒ 单段永不触发、2 包（2×MTU）充分且近乎最小 ✓，
   drain 不推进 `rcv_nxt` ✓。**建议**：若保留动态化，把阈值做成 Engine 字段
   （`Client::start` 时按生效 MTU 算）；若采纳第 6 条则整项撤回。
   **严重程度：低**（多世代才现形，且 1 段差在 10ms delayed-ACK 面内）。

8. **§1.8-3 坑 4 回归专测的形态学（P2.md:172-175）** —— 注入面**成立** ✓：
   `run_shaped_download` 的 DirLink 走**内层明文**（`intercept/mod.rs:3699-3722`：
   client poll→up→`itc.on_plain`；`itc.pump`→down→`client.inject`），

   (a) **必须钉明加在 `down` 链路**——下载形态的数据段在 down，up 只有小 ACK；
   加在 up 上会"注入看着有效、其实什么都没丢"；

   可达"那条兜底 —— 别把这条测试当兜底的验证。另 `DirLink.dropped` 现有断言
   （冷/浅臂 0 丢）不能被 mtu 丢包污染 ⇒ 独立计数（设计已提 ✓）。
   **严重程度：中**。

### 2.4 总评（拍板形态是否成立）

**形态成立，但不能按现稿进 P2b。** 双档（1280 默认 + 1380 opt-in）+ 配置门控 +
分层防线是正确的**风险形态**：默认零变化、收益可消融验证、拒绝方向永远朝 1280，
与"宁可不升"的总纲自洽；1380 这个**取值**经核对依然安全（最坏组合余 25B）。
不成立的是**门控与护栏的实装论证**：L5 在 smoltcp 0.14 上是空操作、手机 stack B
绕过全部门、兜底层只覆盖 IPv4、"恒出"新键撞三道既有契约门、DF 引入新的 UDP
丢包面。按 2.2 的 1/2/3/5 四条（高）整改后本形态可原样落地；其中第 3 条（L5
改 Interface 重建）与第 2 条 (a)（v6 不升档）是本批**最小的确定性安全集**：
前者让出口护栏真生效，后者把"没有兜底的一族"直接排除在升档之外，两者都不依赖
best-effort 行为。**建议 P2b 范围**：TUN MTU（VpnConfig）+ 出口拦截栈 caps 双端
1380 + L2/L3 门 + L4 静态自检（平台分派实现）+ mtuEff（有 link 才出）+ v6 不升；
stack B 升档、L5 运行时降档、ACK 阈值动态化三项移出本批或按整改后形态单列。

### 3.4 两端不一致窗口（rev2）

- TCP：MSS 协商自洽（r1 核实：`effective_mss = min(构造期 local, SYN 落定 remote)`；
  单端升 = 无收益无害）。**出口 caps 1380 + 旧手机（TUN 1280）**：手机通告 1240 ⇒
  出口发送段 ≤1240 ✓；出口 SYN-ACK 通告 1340 ⇒ 手机内核 ≤ min(1240, 1340) = 1240 ✓。
- **入站无 MTU 门**（r1 核实 `iface/ipv4.rs` 无 ip_mtu 引用）：出口 caps 1380 不丢
  对端 1240 旧 MSS 段；反之手机收 1340 段（若出口先升）也由 OHOS 内核本地交付
  容忍（IPv4 输入路径不按接口 MTU 丢本地交付包）。
- UDP：出口下行 = 尺寸由远端决定、与 caps 无关（现状如此）；**手机上行最大外层
  包 1342 → 1442（+100B）**——落在 L3b+兜底的覆盖内（v4 分片可达）。

### 3.5 运行时切换语义（rev2，替换 §1.5）

- 手机：mtuEff 每世代一次（buildVpnConfig 的 readTunStatus 时点 = 接口定型前，
  与 exitIp 同位）；**快路径 tryRebind 维持档位；全量 rebuildTunnel 重新过门**。
- 出口：config 起一次、进程生命周期恒定（L5 出批）。
- OHOS 侧「接口 MTU 建后固定」：无 update/setMtu API（SDK 面，实现时补引）。
