## 总判：**需修订后放行**（3 项高危 + 若干中危折入 v2）

设计主体（浅拆点、SPSC+FIFO、降级内联、整形原地不动）方向正确、与 R1/R8 决议相容，
可实装；**但收益模型与验收目标缺少本仓自身证据支撑（I-1）、唤醒 pipe 在 panic 路径上
会打死进程（G-1）、收工序的 join 上限在 std 下不存在且超时路径未定义（C-1）**——这三项
不解决，实现阶段会出现「拆完没收益 + panic 变成进程死 + 收工卡死/端口漂移」三类返工。

放行条件（最小集）：
1. G-1（SIGPIPE）与 C-1（join/预算）在 §2/§3 写死实现形态；
2. I-1 补一次驱动线程级 profile（或把 T1/T3/T5 设为主门、吞吐门降级为参考）；
3. A-1/A-3/C-4/F-1/B-1 的边界写进设计（不要求改形态，要求写清判据与所有权）。

## ① 选型与背压

### A-1【高】容量 4096 的 Σcwnd 论证不构成上界（只是工程估算）
- 位置：P1-design §3①（91-94 行）；对照 `intercept/mod.rs:39`（MAX_CONNS=1024）、
  `:61`（FLOW_TX_BUF=1MB/流）、`:53`（MAX_UDP_SESSIONS=4096）、R8.md §九
  「滞留队列有界性」段（UDP 过境/DNS 应答/ICMP 回显不走 TCP 窗记账 + 队头阻塞无硬上界）。
- 问题：四个漏洞——(a) **队列不只有 TCP**：UDP 过境/DNS 应答/ICMP 回显按 R8 §九
  自述「不受整形/窗记账约束」，恶意/高频 UDP 面可独立把队列抬满；(b) **重传**：
  发送线程停摆时 smoltcp RTO 重传是**新入队元素**（in-flight 记账不增、队列元素增）；
  (c) **流数**：3200 包 = 4 流 × 1MB txq 的**测速形态**，txq 上限是 1024 流；
  (d) **口径**：1MB 是 tx_buffer（未上线存量）不是 cwnd，高 BDP 形态（intercept 内
  自述 BDP≈2MB）下 Σcwnd/MSS 可超 4096。⇒「正常形态队列永不満」**不成立为不变量**，
  只能作为「4 流测速产品形态下的估算 + 溢出是设计内丢弃路径」。
- 建议：v2 把 4096 改述为「按主用形态（4 流 bulk）估算 + ≥2× 余量」；把 T3 从
  「预测」升级为「观测门（满丢常态必须 0）」；容量常量与 FLOW_TX_BUF/MAX_CONNS
  的推导关系写进注释（防后续调 FLOW_TX_BUF 时容量失配）。

### A-2【中】「丢新不丢老」的 TCP 友好性论证漏了三点
- 位置：P1-design §3①（96-99 行）。
- 问题：(a) **丢新 ≠ 网络尾丢的全部语义**：这是「整形器已按 R8 放行、TCP 已计入在途」
  之后的丢弃，丢的是**已经承诺过的额度**——对端看到的是空洞 + 后续包继续到达
  （dup-ACK/快速重传路径成立，方向没错），但整形器的「放行⇔线上」在过载态断裂；
  (b) **共享队列的公平性**：丢包率 ∝ 到达份额（近似公平），但**队头阻塞不按份额**——
  一个 peer 的 bulk 会把交互型小流（DNS/term/UDP transit）压在最多 4096 包 ≈ 100ms+
  之后，R8 §九 自述「队头阻塞无硬上界」，本设计在其下游**再叠一级**；
  (c) **控制面同队**：握手应答/keepalive 与数据同 ring，满丢会丢握手应答（后果是
  5s 级重试放大，不是单包丢失）。
- 建议：ring 元素带 peer/devTag（≤8B）标签 + 满丢按 peer 归因（首丢记行含 dst）；
  控制面（握手应答/keepalive）与数据分队列或走保留位；HoL 上界写进 §4 不变量声明。

### A-3【中】「一次唤醒取尽可见深度」在积压态会把多拍放行量并成一团——R8 单拍上界被绕过
- 位置：P1-design §2（59-60 行）、§4（176-187 行）；对照 R8 §九（348-354 行
  单拍放行 ≤ burst 的不变量）与 §9.10（团块丢包事故 2MB→dup 260-657）。
- 问题：整形器的不变量是「单次释放 ≤ burst=256KiB」。发送线程若把 2-3 拍积压
  （2-3×256KiB）一次 send_batch 放出，**瞬时团块 = 队列驻留量**，正是 §9.10 花钱
  修掉的形态。字节总速率上界（"任何窗 w 内 ≤ B+R·w"）数学上仍成立（ring 不注入
  字节），但**平滑语义与单拍上界被下游 re-batch 抵消**——这就是「队列事实上成为
  第二级整形器（反向：去整形器）」的实指。
- 建议：单次取队限批（≤ 一拍放行量或 64 包的整数倍）+ 观测「单次唤醒发送字节」分布；
  真正保平滑只能靠发送线程内 pacing（见 I-1）。

### A-4【中】满丢可以避免：高水位→暂停放行 严格优于 tail-drop
- 位置：P1-design §3①（96 行）、§3③（141 行「满即丢，try-push」）。
- 问题：「驱动线程入队永不等待」是对的，但**入队之前还有整形器这一级缓冲**
  （`tx_deferred`，深滞留形态实测 2-3MB）。队列高水位时把包**留在整形 FIFO**
  （不释放）比丢在 ring 更优：不丢包、对 TCP 是真背压（栈内 txq 满 → worker 停写）、
  且整形 FIFO 本就是被 R8 建模/观测的那一级。
- 建议：ring 暴露 `len()` 给驱动线程，超过高水位（如 3/4 容量）时本拍释放退化为
  「只放桶内余量/不放」，满丢保留为**最后一道**（真过载兜底）。若采纳，T3 判据
  需同步改为「高水位触发次数 + 满丢=0」。

### A-5【中】T3 只看满丢、不看驻留，漏掉「稳定排队点」形态
- 位置：P1-design §7 T3（229 行）、§3④（157-158 行）。
- 问题：§9.10 的 17-27ms RTT 事故是**几百 KB 常驻滞留**造成的（深度/R 排队延迟），
  当时满丢=0。本设计只把「满丢 ≠ 0」当红信号，**驻留 3000 包 + 满丢 0** 才是更
  可能的病态形态（发送线程吞吐略低于整形放行率）。
- 建议：判据改为「稳态队深 p50/p99 + 驻留字节」，常态门 = 队深峰 ≪ 一拍放行量
  （256KiB ≈ 200 包）；常驻 >3000 包与满丢同样判红。

## ② FIFO 保序

### B-1【中】降级切换「先 drain 再内联」无乱序窗口——成立，但要状态机化 + 补两条边界
- 位置：P1-design §3②（117-120 行）；对照 `engine.rs:1170/1301/1331` 三个 send_wire 调用点。
- 问题：论证成立（单生产者 + 降级后不再入队 + drain 先于本批）。但两点未写：
  (a) 判据必须是**一次性的显式模式位**（`TxMode::{Thread, Inline}`），不能每包读
  `tx_alive`——否则「读到旧值 true → 入队」与「置 false 后 drain」之间存在
  「入队了但没人发」的窗口（包不丢，但在 ring 里躺到下一次 drain，延迟不可控）；
  (b) **panic 时已被 pop 未 send 的包是真丢**（洞，不是乱序）——设计要写明这是
  接受语义（与 send_batch 短返余量丢弃同族）。
- 建议：模式位 + `debug_assert`（Inline 模式下 ring 必须空且不再 push）；
  丢包计数把「panic 时在途批」单列。

### B-2【低】腿路径/主 socket 跨路径确实存在窗口（endpoint 迁移），但 WG 重放窗吞得下
- 位置：P1-design §3②（121-125 行）；对照 `bind.rs:635-679`（腿派发/#17 按 endpoint 判定）。
- 问题：常态下每个 peer 的包只走一条路径（endpoint 决定），无乱序；**endpoint 迁移
  窗口**（腿↔直连切换）里，先入 ring 的旧路径包会被后 inline 发的腿包越过。
  今天不存在（同线程同拍串行），拆分后窗口 = ring 排空延迟（常态 µs 级）。
- 建议：把窗口量化写进设计（「≤ ring 排空延迟；WG 重放窗 2048 包容忍」），
  并在降级/积压态下注明窗口可放大（积压 4096 包 ≈ 100ms+）。

### B-3【低】STUN/probe inline 同 socket 并发——论证可靠，但清单不全
- 位置：P1-design §2 表（72 行）、§3②（123-125 行）；对照 `bind.rs:315-319`
  （probe 应答在 `process_packet` 内裸 `send_to`）、`bind.rs:760-762`（send_raw_to）、
  `engine.rs:515-517`（relay-leg 线程已持 clone fd 同 socket 发送——**先例在册**）。
- 问题：UDP 逐数据报原子性 + 无同流序约束 ⇒ 论证成立，且仓内已有第二个线程
  同 socket 发送的既成事实（D4#1）。漏的是：§2 的进程清单里没有 probe 应答路径。
- 建议：§2 清单补 probe 应答；「发送线程独占主 socket 发送面」改为「独占**数据面
  主路径**发送执行」（见 E-1）。顺带登记：inline 发送在 ring 积压把内核 sndbuf
  压满时更易 EAGAIN（非本批新增，排障时别误判）。

## ③ 生命周期 / 收工

### C-1【高】「join 上限 2s，与驱动线程收工同款」——后者不存在，前者 std 无原生支持
- 位置：P1-design §3③（138-140 行）；对照 `engine.rs:779-782`（`h.join()` **无超时**）、
  `engine.rs:849-853`（Drop 再 shutdown(2s)）、`engine.rs:402-407`/`relayleg.rs:120-123`
  （仓内辅助线程惯例 = stop 位 + detach，不 join）。
- 问题：std 的 `JoinHandle` 没有 join_timeout。若按「超时放弃」实现为
  `is_finished()` 轮询 + drop handle（=detach），**泄漏的是 tx 线程手里的 dup fd**：
  socket 仍绑定在原端口 ⇒ 角色重启时 `listen_with_fallback` 退让到 port+1 ⇒
  token 公布端点漂移（`bind.rs:202-207`），daemon 内重启尤其危险。
- 建议：v2 二选一并写死：(a) 不设超时，靠「stop 位 + 非阻塞 socket（最坏一次
  send_batch ~µs 级）」论证 join 必返，只在超时（如 5s）记行不放弃；(b) 真超时则
  **不 detach**：标记泄漏并在下次角色启动前拒绝重绑同端口（或进程级退出）。
  同时把「总收工预算 = stop_grace + drain + join」写进 §3（见 C-2）。

### C-2【中】收工序预算与 stop_grace 是相加关系，可能超 supervisor 预算
- 位置：P1-design §3③（136-140 行）；对照 `engine.rs:1263`（deadline = now+stop_grace）、
  `serve_cli.rs:484`（grace=2s）、`unified_cli.rs`（STOP_GRACE=10s）。
- 问题：宽限循环吃满 stop_grace 后，drain(≤2s)+join(≤2s) 是**额外**的 ⇒ 最坏
  2+4=6s（前台）或 10+4=14s（daemon）。launchd/systemd 的 kill 超时窗内被 SIGKILL
  ⇒ sock 文件/state 半清（`shutdown` 的 ⑤ 在 join 之后）。
- 建议：drain/join 的 deadline 从**同一个**收工 deadline 派生（剩余预算制），
  并把总上界写进设计；`Drop` 的 2s 形态同样适用。

### C-3【中】spawn 失败 / `tx_alive` 初值语义未定义
- 位置：P1-design §5 P1b-3（195 行）、§3③（129 行）。
- 问题：若照抄驱动线程的写法（`driver_alive` 先置 true 再 spawn，
  `engine.rs:550-585`），spawn 失败 ⇒ alive 恒 true ⇒ 永不降级 ⇒ 包在 ring 里堆到
  满丢，且没有任何故障行。驱动线程那边是 `.expect("spawn")`（直接 panic），
  tx 线程按本设计哲学不应 panic。
- 建议：`tx_alive` 初值 false，spawn 成功回调置 true；spawn Err ⇒ 直接 Inline 模式
  + 一次性记行（复用 §3③ 的降级行）。

### C-4【中】drain 超时后禁止 producer 侧 `clear()`
- 位置：P1-design §5 P1b-1（193 行 API 列表含 `clear`）、§3③（137-138 行「超时记行放弃」）。
- 问题：ring 是 SPSC；consumer 仍活着时 producer 调 `clear()`（drop 未消费元素）
  是数据竞争（consumer 可能正在 `assume_init_read` 同一槽）。「放弃」释放也有歧义：
  先 pop 后 send 的批已在 consumer 手里、ring 深度=0 ≠ 已发出。
- 建议：`clear` 仅允许在 consumer 确认停止（join 返回/Inline 模式）后调用；
  超时路径 = 不 clear、只 stop+join，剩余元素随 ring 结构 drop（并保证 Drop 会
  逐个 drop Vec，不泄漏）。

## ④ 插桩面

### D-1【中】「UDP 出站」字符串面不破坏，但**口径变了**，PERF-AB 的跨批可比性要回写
- 位置：P1-design §3④（149-151 行）；对照 `engine.rs:1210-1256`、`engine.rs:1212`、
  `bind.rs:708-714`。
- 问题：已核实消费者只有 engine 5s 行 + `bind.rs:1069-1078` 单测（`tx_bytes`），
  `tools/` 与 status/daemon **无 grep 消费者**（`status_bits` 只读 intercept 原子）。
  但 `tx_calls` 的语义从「每次 send_wire 调用（每拍 1-3 次）」变成「每次唤醒」
  ⇒ PERF-AB §9.10/§9.11 引用的「均批/单调用峰值 130-136/桶分布 32-63」与新读数的
  分母不同，**不可直接对比**。
- 建议：新行沿用字符串但补口径标识（如「调用（每唤醒）」）；PERF-AB 引用处加
  「P1 后口径」注记；或在发送线程里同时保留「每 send_wire 批」与「每唤醒批」两个
  计数（前者由驱动线程投递时记，成本一个原子加）。

### D-2【中】「5s 行停更 = 发送线程死了」不成立；行由哪条线程打要二选一
- 位置：P1-design §2（60 行「5s 观测行」）、§3④（147-151 行）、§8（238 行
  「发送线程行消失本身就是信号」）。
- 问题：设计同时要「pselect 空窗长眠**无超时**」和「发送线程打 5s 行」——空闲但存活的
  线程不会打行，最后一个窗口的统计也永远不 flush；且行由 tx 线程打时，tx 线程的
  `dlogf` 与驱动的行在 sink 侧交错（`logfile.rs:26` Mutex 只保单次调用原子）。
- 建议：二选一并写死：(a) **驱动线程打**（它每 1-5ms 必醒，窗口最稳），读共享原子；
  则「行消失」信号废除，liveness 由 `tx_alive=false` 降级行承担；(b) tx 线程打 +
  pselect 带 5s 超时。推荐 (a)——顺带把共享原子面缩到实际被读的字段。

### D-3【低】共享原子面可缩小；无遗漏消费者（已核）
- 位置：P1-design §3④（152-155 行）。
- 问题：若行改由驱动线程打（D-2(a)），则 tx 线程只需暴露 `tx_alive` +
  被读的那几个累计计数，窗口峰值/直方图可留 tx 线程私有（消费即清）。当前设计把
  全部字段都做成 `Arc<AtomicU64>` 是多余的。
- 建议：按「谁读谁定域」重列字段表；`tx_bytes_leg` 与主路径分列正确（腿路径单测
  `bind.rs:1069-1078` 断言的是腿路径增量，改名后需同步）。

## ⑤ 与 R1 决议的演进关系 / 隐藏共享可变状态

### E-1【中】「各自独占自己的 fd」只在 fd 号层面成立：同一 underlying socket 的内核状态是共享的
- 位置：P1-design §3⑤（168-173 行）；对照 `bind.rs:607-618`（repin 作用于 socket）、
  `bind.rs:185-201`（SO_SNDBUF 4MB，运行期不变）、`engine.rs:515-517`（relay-leg 已有 clone）。
- 问题：dup fd 共享 file description/socket 状态：SO_SNDBUF、钉卡（`repin_to`
  运行期会被看护调用！）、内核发送缓冲与队列、源端口。这些都有内核级串行化，
  **不是数据竞争**，但语义上「独占」不成立；且 `repin_to` 与 ring 里已判定的包存在
  「决策后环境变化」窗口（同 B-2 族）。
- 建议：把声明改成「发送线程独占主路径的**发送执行**；socket 内核状态由 fd 共享、
  由驱动线程单方变更（钉卡/缓冲）——变更不引入数据竞争，但会作用于在途/已入队包」；
  隐藏共享态清单列全：socket 内核态、`Logf` 内部 Mutex、`PSELECT_BROKEN`
  （`engine.rs:939` 模块级 static，两线程复用需分面）、`udpbatch` 的 `NO_BATCH`
  OnceLock（只读，安全）。

### E-2【低】「全路径无 Mutex/RwLock」要把日志面排除
- 位置：P1-design §3⑤（171-172 行）；对照 `lib.rs:12`（Logf = Arc<dyn Fn + Send + Sync>）、
  `logfile.rs:22-32`（RotatingWriter = Mutex<Slot>）。
- 问题：tx 线程打观测行必然进 `Logf` ⇒ 触 Mutex（跨文件写，可能阻塞）。不在热路径，
  但断言「无锁原语」不严谨。
- 建议：限定语「**数据面热路径**无锁；观测面复用既有 Logf（内部锁，与现有多线程
  日志同款）」。

### E-3【低】`send_wire` 的借用面
- 位置：`bind.rs:629`（`&InboundOut`）；P1-design §3①（104-106 行「move 入队」）。
- 问题：现签名只有不可变借用，ring 元素若想复用 `out.wire` 里**已分配的 Vec**
  （`device.rs:361-366/388`：每个 wire 元素本来就是一次 `to_vec`），必须改
  `&mut`/按值 + 帧化下沉到 tx 线程（原地写 2B 帧头需 device 侧预留 headroom）。
- 建议：作为 §8「Vec 回收 ring」的**更简替代**评估：device 侧分配留 2B 头 +
  `send_wire(&mut …)` 移动原 Vec 入队 + tx 线程复用 staging 帧化 ⇒ 每包额外分配归零
  （现状 = 1 分配/包，本设计 = 2 分配/包）。注意腿路径/`frame_bytes` 同步改造与
  `out.wire` 前缀不变量。

## unsafe 面（MaybeUninit + 原子序）

### F-1【中】SPSC 规格不足，v1 只给了形态没给不变量
- 位置：P1-design §3①（86-90 行）、§8（237 行）、§9（247-248 行）。
- 问题：缺项——(a) 索引语义（建议单调 usize 递增 + 2^n 掩码，4096 正好 2^12）；
  (b) 发布/消费的 Release/Acquire 配对点要逐条写（写槽→`tail.store(Release)`；
  `tail.load(Acquire)`→读槽；读槽完→`head.store(Release)`；`head.load(Acquire)`→复用槽）；
  (c) 双端缓存的方向写反了/有歧义——**producer 缓存 head（消费者的回收游标）、
  consumer 缓存 tail**，且「抗伪共享」需要 `#[repr(align(64))]` 包裹 + 双端各自
  独占 cache line，光缓存不解决；(d) Drop 语义（含元素时逐个 drop，不泄漏）；
  (e) 满/空判定与 `len()` 的快照口径（观测用，允许陈旧）。
- 建议：把 §8 的「逐点论证」提到设计正文（评审后即实装基线）；单测补
  「丢失唤醒/压满-排空 soak」与「Drop 后无泄漏（drop 计数探针）」。
  备选方案（`Mutex<VecDeque>` + try_lock 或 `std::sync::mpsc::sync_channel` 的
  `try_send`）建议保留在 §8，但注明其代价（锁进热路径，与「热路径无锁」声明冲突），
  避免实现期随手换掉。

## 唤醒 pipe

### G-1【高】panic 后写断管 = SIGPIPE 打死进程（含 daemon 全体角色）
- 位置：P1-design §2（56 行）、§3③（129-135 行的降级故事）、§5（194 行「pipe2 O_NONBLOCK」）；
  对照 `main.rs:35-39`（**显式把 SIGPIPE 恢复 SIG_DFL**）、`pool.rs:301-302`
  （仓内原话：「主进程对 SIGPIPE 已恢复默认处置，裸写不带此 flag 会打死进程」）、
  `pool.rs:129/134/179`（worker 退出时 `close(wake_r)`）、`wgcore:1085-1095` 与
  `relay:334-341`（仓内先例 = `libc::pipe` + `fcntl(O_NONBLOCK)`，非 pipe2）。
- 问题：tx 线程若以 `OwnedFd` 持有读端（地道 Rust 的自然写法），panic 展开即关闭读端；
  驱动线程紧接着的任何一次唤醒 `write` ⇒ **SIGPIPE(SIG_DFL) ⇒ 整个进程死**。
  这把 §3③ 的「panic 只降级、隧道不中断」直接推翻；daemon 形态下还会连坐
  client/relay/term 角色。窗口真实存在（驱动读到 alive 旧值 → 写 → 线程才置 false）。
- 建议（任一，v2 写死）：(a) 改 `socketpair(AF_UNIX, SOCK_DGRAM)` +
  `send(…, MSG_NOSIGNAL)`（与 D-1 低-8 的仓内惯例一致）；(b) 保留 pipe 但读端
  `Arc<OwnedFd>` 双端各持一份（驱动侧那份保证读端永不关闭）+ 写侧仍处理 EPIPE；
  (c) 沿用仓内裸 fd 先例（不 close，泄漏 2 fd/生命周期）——须显式写明「故意泄漏」。
  **不要**依赖「进程全局忽略 SIGPIPE」——`main.rs` 已按 Go 语义恢复默认。

### G-2【中】唤醒协议的次序不变量没写：丢唤醒（睡死）/残留字节（空转）二选一都会踩
- 位置：P1-design §2（56 行「EAGAIN = 已有 pending 唤醒，天然合并」）、§3④（156 行）。
- 问题：EAGAIN 只在 pipe 写满时发生，**合并实际靠 pending 位**（设计里叫「先查 pending
  位」）。正确次序必须显式：producer = `push → if !pending.swap(true, AcqRel) { write }`；
  consumer = `read 到 EAGAIN（读干管道）→ pending.store(false) → 取队到空 → 无包才 pselect`。
  次序错则两类故障：consumer 只读 1 字节 ⇒ 管道残留 ⇒ pselect 恒可读 ⇒ 空转；
  pending 清理与取队次序颠倒 ⇒ 丢唤醒睡死（stop 也唤醒不了 ⇒ C-1 的 join 卡死）。
- 建议：次序不变量写进 §2 + 双线程丢失唤醒 soak 单测（同 G-1 的 (b) 面）；
  仓内已有「读干管道」先例可抄：`pool.rs:155-160` 的 `while read(…) > 0 {}`。

### G-3【低】pipe2 在 macOS 不存在（本地出口/A-B 平台直接编不过）
- 位置：P1-design §5 P1b-2（194 行）；libc 0.2.190 只在 linux_like/fuchsia/redox/
  freebsd/netbsd/solarish/cygwin/hurd/nuttx/vita 声明 `pipe2`，**Darwin 无声明**。
- 建议：改口径为 `libc::pipe` + `fcntl(F_SETFL, O_NONBLOCK)`（`pool.rs:415-419`、
  `wgcore:1085-1092`、`relay:334-341` 三处先例）；或 `pipe2` 仅 linux 分支 +
  darwin 回退（不值得，统一写法更简单）。
- 顺带登记（非本批范围）：`pool.rs` 的 worker 退出会 close 读端，而
  `WorkerPool::send_for`（:456-462）无条件写 wake ⇒ 同类 SIGPIPE 隐患在册。

## 与 R8 整形不变量的边界

### H-1【中】速率类不变量成立，平滑/单拍类不变量在过载态失效——§4 要写明
- 位置：P1-design §4（176-187 行）。
- 问题：ring 不注入字节 ⇒「任何窗 w 内线上深度 ≤ B+R·w」仍成立（数学上）；
  但 (i) 单次放行 ≤ burst 的**单拍上界**可被 A-3 的积压 re-batch 绕过；
  (ii) 8r pacing 的「按期散布」被下游合并抵消；(iii) 整形器的「放行 ⇔ 最终发出」
  在过载/降级态断裂（整形器不知道 ring 深度）。
- 建议：§4 增一节「过载态的语义降级」：列出仍成立/失效的不变量各一条 + 判据
  （稳态队深、单次唤醒发送字节、满丢）。

### H-2【低】整形器拿不到 ring 深度 ⇒ 无法背压（A-4 的接口前提）
- 位置：`intercept/mod.rs:2092-2118`（`tx_pacing_pending`/`tx_shape_wait` 只读
  `tx_deferred`）。
- 建议：若采纳 A-4，把 ring 高水位作为 `tx_shape_wait` 的第 4 态（或驱动循环侧
  短路释放），并在整形观测行加「ring 深度」段——这样「两级缓冲」在观测面上是
  一条链而不是两个孤立数字。

## 收益模型与验证面

### I-1【高】验收目标与归因证据错配：本仓自己的数据不支持「sendto 占住驱动线程」的收益上限
- 位置：P1-design 开篇（5-7 行）、§0（12-15 行收益②）、§6.3（215-219 行验收 ≥35MB/s）、
  §7 T2（228 行 ≥15%）；对照 PERF-AB §9.3（186 行：**出口进程 CPU 全部 0.0%**、
  「78% sendto 是线程内占比非核占满」「离饱和差两个量级」）、§9.10 ④（356-364 行：
  剩余缺口归因 = **拍粒度 × 空口交织 + 接收端 ACK 时钟**，修法是发送循环按时戳散布）、
  §9.11（8s 拿到 +39% 后才轮到出口侧）、§9.12（TUN 路径 B/A 0.87 无缺口）。
- 问题：本批只搬「密文→sendto」，**不动拍粒度、不动 ACK 时钟**——正是 §9.10 点名的
  剩余两个因子里它一个都不碰的那部分；而「sendto 占住线程」这条前提被 §9.3 的
  0.0% CPU 直接顶住（78% 是线程内样本占比，不等于墙钟占用）。逐包 sendto 的
  ACK 消费延迟剂量（每拍 sendto 时长 / 到达 ACK 等下次 drain 的概率）**从未测过**。
  照此，T2(+15%) 与 ≥35MB/s 门都缺依据，真机判红时无法区分「归因错」与「拆分无效」。
- 建议：(a) 开工前补一次**驱动线程级** profile（`sample` 线程面或
  `HOMEWAY_*` 计时）：每拍 sendto 时长占比 + 拍内 ACK 到达时刻，把 78% 换算成
  墙钟/延迟剂量；剂量 ≪ 10% 就先做发送线程内 pacing（那才是 §9.10 ④ 的对症面，
  且浅拆恰好把发送循环交出来了），而不是先搬线程；(b) 把 T1/T3/T5（机制判据）
  设为**主门**，吞吐 ≥35 降为参考（§6 的「或带数据链的架构结论」提到主位）；
  (c) 若仍按原设计开工，§7 预登记「无收益」分支的归因路径（避免事后解释）。
  说明：浅拆并非无价值（批量化归宿、降级内联、Android/Linux 出口 sendmmsg 面），
  但**它的收益量级需要重新声称**。

### I-2【中】T1 的判据当前不可测
- 位置：P1-design §7 T1（227 行「ACK 团到达→cc 行推进的间隔收窄」）；对照
  `intercept/mod.rs:1366-1460`（cc/tcp 观测行是 5s 窗累计差分，没有到达→推进时延测点）。
- 问题：既有插桩测不出 T1 描述的量；P1b-4 的插桩清单（§3④）也不含它 ⇒ T1 判不了红。
- 建议：要么把 T1 改成可测量（发送线程侧「单次唤醒发送字节」+ 驱动侧「每拍收包数」

## P1 定位记录（2026-10-06 接棒批；根因已修 + 全量 Queued 恢复 + 本地全绿）

### 根因一（主因）：唤醒合并位 `pending` 双实例——首个排空窗之后**再无唤醒字节**

- **代码位置**：`server/bind.rs` `tx_start`（实装首版，commit 722dfaf 起）。
  线程闭包按 move 捕获了局部 `pending`（消费侧清的旗），而 `QueuedFace`
  构造时写的是 **`Arc::new(AtomicBool::new(false))`——现 new 的第二面旗**
  （生产侧 swap 的旗）。对照同函数内 `stop`/`alive`/`dlogf` 全是 `Arc::clone`
  进闭包、原件进 `QueuedFace`——唯独 `pending` 直接 move 导致外层不可用，
  构造处补了个新的满足借用检查，两旗自此各打各的。
- **失效链**：①首次 push：生产侧旗 swap(false→true) 返 false ⇒ 发唤醒字节；
  发送线程醒来排空，排空后在**线程闭包那面旗**上 store(false)（本来就是
  false——空操作），读干 socketpair、查空、进 `poll(-1)` 长眠。②此后每次
  push：生产侧旗 swap(true→true) 恒返 true ⇒ **永不再发唤醒字节**（该旗无人
  再清）⇒ 包永驻 ring，发送线程睡死。⇒ **整个进程生命周期只有一次唤醒**。
- **逐条对上前棒全部观察**（为什么每条都是误导）：
  - 「Queued 全量死锁、客户端 rx=94B」——94B = 2B 腿帧头 + 92B WG 握手
    response（`[bb,00,02,…]`，WG type 2 = response）：response 恰是**首条**
    入队包、落在唯一的排空窗内 ⇒ 发出且被客户端**接受**（本批修复后同一 94B
    包成为客户端 117k 包流的第一包，`warmup pong: 就绪（判据=wg）`——「WG 层
    拒收」是误诊，拒收从未发生）；死锁的真身 = response 之后的**一切**（探测
    应答/传输数据/keepalive）永驻 ring ⇒ 客户端 connect 判据永不满足。
  - 「混合形态 RST 74B 接受 ✓ / SYN-ACK 86B 收不到 / ENCDBG 28 wire vs
    3 批」——一切取决于**是否落在首个排空窗内**：窗内（流程早段的 dial/
    RST）发出且接受；窗外（speedtest 的 SYN-ACK 及之后全部）永驻。28 产出
    vs 3 批发出 = 首窗吞掉的部分 vs 其余。「74B vs 86B 只差 12B」的分野是
    **流程顺序**不是包长/内容——前棒方向 2（12B 差异）与方向 1（客户端
    拒收错误码）都不必查：包没问题，是根本没发。
  - 「唤醒→排空延迟 0ms（同毫秒）」——量在唯一那次会发生的唤醒上。
  - 「e2e 单测 3000 包全收保序全过」——紧循环连推全部落在首窗内，钉不住
    本形态（本批回归测试的由来）。
  - 最小复现 bin/hex 对拍/stash 对照全过——它们都不经过 pending 协议。
- **修复**：闭包内 `Arc::clone(&pending)`、原件 move 进 `QueuedFace`——
  两端共用同一实例（G-2 次序不变量本就正确，坏的是「同一面旗」前提）。
