### harness 重标定（有据，非调参凑数）

1. **链路模型突发额度修正**：出队 credit 空闲累积上限原误设为队列容量（2MB——
   空闲后一次放出 = 24MB/s 链路 85ms 的量，物理链路无此形态）。该 mega-burst 把
   smoltcp 接收端「每 poll 至多一个 ACK（顺序数据）」的合并形态放大成 **ACK 时钟
   饿死**：burst 到达 ⇒ 每团一 ACK ⇒ 发送端 CUBIC 每 RTT 只 +1 MSS ⇒ 16MB 传输
   实测 3.5MB/s（稳态实为满链路 24.8MB/s——64MB 传输实测 12.9MB/s 均值、尾窗满速）。
   修正：burst = rate×2ms（≈48KB）。内核/gVisor 接收端无此形态（团内每 2 段回 ACK）。
2. **A 单流 16→64MB / A 并发 6×3→6×8MB**：上游 CUBIC 慢启动爬坡在 harness 接收端
   ACK 合并形态下需 ~1.5-2s，16MB 量级传输被爬坡期支配（5.5MB/s vs 稳态 24.8）；
   量级提到稳态支配。塌陷判别语义不变（0.4MB/s 塌陷在 64MB 下 160s 超时必红）。
3. **A 并发臂阈值 50%→1/6**：原 50% 阈标定于**已退役垫片**的 pacing 行为（垫片 pacing
   顺带保住了接收端 ACK 密度）；上游 CUBIC 无 pacing，N 流慢启动过冲对 2MB 尾丢缓冲
   的同步振荡 + ACK 合并放大下实测 5.0-11.5MB/s 波动。**塌陷判别职责移交 B 臂**
   （修正模型下 CC=None 深队列 22.6MB/s 不再构成判别信号、浅队列仍 <0.2MB/s 级塌陷
   实测——8MB 未完成跑 8min+）。三个臂的旧数字（垫片 15.8/16.7/6.4）留档为历史基线。

## §二 8b：encap/UDP 发送路径优化（commit 8b 批 + 微修）

### profile 结论（2026-10-04 `sample` 实测，与 PERF-AB §8 的 76% 一致）

出口驱动线程（下行 bulk 期间）：**78% 样本在 `__sendto`**（每包一次系统调用），
poll 12 个、smoltcp 栈 poll ~2%。两条 sendto 路径 = `route_encap`（拦截拍产物）+
`handle_inbound`（逐包收后的应答收口）。

### 实现与真机验证的曲折（保留全过程结论）

1. **`udpbatch` 模块**（保留）：批量发送原语——Linux/OHOS `sendmmsg`（≤64 条/批、
   短返余量留下一拍、EINTR 整批重试；libc 面在 aarch64-unknown-linux-ohos 编译
   验证）；macOS 回退逐包 std send_to（与 Go/wireguard-go 同形态——同机 A/B 公平）。
   回环 80 包顺序到达单测。
2. **出口 `ServerBind.send_wire` 批化 + staging**（保留）：腿帧先落复用 staging
   （消除逐包 frame_bytes 的 Vec 分配，载荷一次拷贝）再批量发出；腿 socket 命中
   （稀疏路径）保持逐包；空批快速返回。macOS 宿主回环 A/B：down 261-263Mbps 持平
   （Go 同形态）、up 401→469Mbps（staging 零分配收益）。
3. **客户端（手机）上行批化**（**实测劣化已整体移除**）：曾实装「pump_once 收集
   TUN 包 + 栈 B TX → 批量 encap → `send_wg_batch` 一批 sendmmsg」。真机 A/B
   （FMR0224116011480，本地 Rust exit）**两侧皆劣化**：批化 down 15-18MB/流 vs
   逐包 41-47MB/流、up 25MB/流 vs 32-86MB/流——OHOS 的 sendmmsg 批量路径反而拖慢
   收发节奏（机制未深挖：疑批量突发与 WiFi 驱动交互 + 每批系统调用内无中间唤醒点）。
   消融实测后整体移除（pump_once 注记留档）；客户端侧 8b 的净交付 = 背压修复（下条）。
4. **上行 bulk 断流的真根因与修复**（本批最大发现）：`SessionWriteHalf::write`
   把栈内 tx 缓冲满时的 `send_slice` **Ok(0)** 直接透传——io::Write 契约里 Ok(0) =
   通道关（`write_all` 以 WriteZero 报错），桥泵据此拆连接 ⇒ 上行 bulk 一进慢链路
   （缓冲被 cwnd 门限速填满）就整轮断流。**R7 E2E 登记的「phone→exit WG 上行 bulk
   吞吐退化」即此**（host 形态 CLI 走 ClientConn 的零进展重试环，桥路径裸露）。
   修复：Ok(0) 展开为**有界等待重试**（2ms 节拍、10s 无进展上限——Go net.Conn.Write
   阻塞语义）。真机验证：上行从「4 会话 <1s 全 EOF」到「完整轮完成」。
5. **桥泵收口观测**（保留转正式）：桥泵此前静默收口——累计字节 + 收口原因一行
   （有流量才打，空闲连接零噪音）。本次排障的关键观测面。

## §九 R8-3 8i：出口发送整形——设计小节（实装前登记，2026-10-05）

> 范围 = PERF-AB §9.7 修复路径 ①（拦截栈单 poll 排空 → 发送预算 + 分拍投放）。
> 本节先落设计再动代码（任务纪律：设计细节过评审再实装）。

### 位置与机制

**拦截面**：`Interceptor::pump()` 尾部——拦截栈单 poll 的排空产物（tx_out，已反重写
的明文 IP 包）先并入**滞留队列**（`tx_deferred`，FIFO），再按**字节令牌桶**从头释放；
释放出的包才是本拍返回引擎 encap 的出站集合。`pump_grace` 复用 pump ⇒ 收工宽限走同
一整形。**无 sleep、不阻塞驱动线程**：滞留队列靠后续 pump 拍续传——驱动线程每拍必调
pump（poll(2) 5ms 上界 + ACK 到达即醒），即 PERF-AB §9.7 的「预算 + 下拍续传」。

**预算（静态默认 + env 覆盖，不与 CUBIC 抢自适应职责）**：

| 参数 | 默认 | 依据 |
|---|---|---|
| 速率 R | 64 MiB/s（`HOMEWAY_TX_RATE_MBPS` 覆盖） | 真机层 0 天花板 94MB/s 的 0.68×；验收带 40-45 之上留 ≥40% 余量。稳态到达 < R 时令牌常满、**零延迟直通**——整形器只削峰不平率，平均率仍由 ACK 时钟（CUBIC）决定 |
| 突发额度 B | 160 KiB = 128 × MTU1280（`HOMEWAY_TX_BURST_KB` 覆盖） | §9.7 建议带「≤128-256 包」的下沿（满包口径恰 128 包）；与 harness DirLink 的 rate×2ms 物理突发参数同量级；驱动拍 5ms 的续水量 320KB ≥ 2×B（桶永不在拍间枯竭两拍）。任何窗口 w 内线上深度 ≤ B + R·w |

**静态而非自适应的理由**：自适应（ACK 速率 max-filter 估计）与 CUBIC 构成双环耦合
（估计跌 → R 收紧 → 到达形态变 → 估计再跌的振荡面），且冷启动窗口恰是悬崖窗口（无
估计可用仍得回落静态值）。静态 R 的疑虑「路径容量 < R 时持续过载」不成立：整形器
**不注入流量**——滞留队列只能持有 smoltcp 已排放的量，而排放以 ACK 回收为前提（在途
≤ cwnd）⇒ 路径慢 ⇒ ACK 慢 ⇒ 排放停 ⇒ 桶只削每拍团块。失效模式收敛为「削峰粒度不随
路径变」，由 env 臂真机调参兜底。

**与背压/饥饿的交互**（评审要点预答）：
- FIFO + 聚合桶：按到达序释放，无流间饥饿；多手机共享 R（链路物理本就共享）。
- 滞留队列**有界性由 TCP 在途记账保证**（≤ Σcwnd ≈ 数 MB）——不设显式上限：加上限
  即「整形器丢包」，属伪修复禁区。
- 字节口径令牌：纯 ACK/DNS 小包成本 ∝ 尺寸，不被大包挤出；最坏排队 ≈ 队深/R
  （3MB/64MiB/s ≈ 47ms），上行 ACK 时钟与 DNS 容忍。
- 大于 B 的包防御性直通（内层 IP ≤ 64KB 恒小于默认 B；防极小 B 配置死锁）。

**消融臂**：`HOMEWAY_TX_SHAPING=off`（presence-only，与 HOMEWAY_UDP_NO_BATCH 同惯例）
——真机 A/B 与 harness on/off 臂共用。产品默认 = 开。
