### 5.1 逐层读数表

| 层 | 读数（本批） | 判据式命中？ |
|---|---|---|
| **L0 环境锚** | 层 0 中位 5.997 s（44.76 MB/s） | 命中「<2× 隧道中位」的绝对限制注（§3.1）⇒ **绝对值只登记、判据用比值**（本批主判据本就是比值口径） |

### 5.2 命中层与结论

**命中唯一层族 = L3（设备单核贴顶）+ L4（逐包成本 2.23×）+ L5（TUN 承载路径 vs 自连路径方向相反）**，
即：**QUIC 岛在真机 TUN 数据面上的逐包成本约为 WG 档的 2.2×**——在设备单核已贴顶（≈1.0–1.1 核）的前提下，吞吐直接反比下降（23.5 → 11.4 MB/s）。环境（L0）、出口（L2）、拥塞/ACK 时钟（L4 计数面）、构建档位（L6）**均清白**。

**M7 决策输入（代价估计，M6 不改代码）**：
1. **接受差异**：真机 TUN 吞吐 0.485×，但自连路径（files/term/speedtest 与 App 直连面）↓39 MB/s、断线恢复 2.45 s（优于旧臂 E1 口径 26.7 s）⇒ 是否可接受取决于用户对「全局代理 TUN 吞吐」的期望。
2. **低成本修复候选（需另开批 + 用户点头）**：设备侧岛热路径的逐包成本（`crates/homeway-quic/**` 的 TUN 转发链）——归因落到该面即为**下一个性能批的入口**；本批只给入口不给方案。
3. **另开优化批**：若需达到 ≥0.95×，按 2.23× 的逐包成本差，期望修复幅度需 ≥2.3×（量级参考：M5 实验室口径 quic 12.929 µs/包 vs raw 4.885 µs 的 2.65× 差——**跨口径不可互引**，仅作量级参照）。

### 12.1.3 定论：**哪一段占 2.23× 的主要份额**

- **系统调用面 = 81%**（TUN 写 35.2 + TUN 读/等 23.2 + UDP 收 22.5 + UDP 发 10.1）；岛内用户态工作（泵 + quinn
  residual + 通道 + 检包）≈ 19%。
- **QUIC 档 − WG 档 ≈ 62 µs/单元**，逐项：UDP 收发面 **+24**（WG 走 `recvmmsg`/`sendmmsg` 批处理、且收发在引擎线程内联）；
  回程**多一跳**（泵任务 + 有界队列 + 独立写线程）+10；读面 **read+poll 对** +9.5（WG 读线程 13.7 vs 本档 28.5）；
  quinn proto/crypto/运行时 +10；ACK 面（WG 无 ACK）+8。
- **为何自连面无损而 TUN 面 2.23×**（L5 的反推）：自连面（STREAM/speedtest）**不经过 TUN fd**，也没有
  DATAGRAM 的「每包一次队列投递 + 独立写线程」结构——折算成本 ≈ 32 µs/1252B；TUN 面每包**多付 4 次 TUN 系统调用
  + 一跳线程**（≈ +70 µs）⇒ 「TUN 承载路径 vs 自连路径方向相反」由**系统调用面**解释，与出口侧/环境无关（承 M6 L2/L0）。

## 12.4 未达标：量化结论（差多少 / 卡哪段 / 需要什么）

1. **差多少**：目标 ≤56.4 µs/单元（T6 口径）或热态 ≥0.95× 旧臂（本会话口径 ≥19.0 MB/s）；现状 **92–98 µs/单元**
   （本会话 10.54 MB/s = 0.527×）⇒ **仍需再降 ~42%**。
2. **卡哪段**（修后逐段表）：TUN 写 35.9 + TUN 读面 9.3 + UDP 收 22.8 + UDP 发 ~10 ≈ **78 µs/单元（占 85%）**
   是**同设备同内核的系统调用面成本**——WG 档同样要付 TUN 写/读（其引擎 35.4 µs/单元几乎全 = TUN 写），
   但它没有 QUIC 的 UDP 面（批处理 + 引擎内联）与 ACK/DATAGRAM 面。
3. **还差多少成本 / 需要什么才能动**（三条结构性前提，本批均**不可得**）：
   - ① 设备内核 UDP 收发的**真实批化**（GSO/GRO 或内核侧聚合）——本批 `recvmmsg`（用户态多段）实测**无增益**，
     说明每包成本在**内核每包处理**，用户态批处理到达不了；
   - ② 回程**不再每包一次 TUN `write`**（内核 tun 批量写 / `io_uring` / 驱动级聚合）——产品面不可得；
   - ③ **减少每字节的包数**（增大内层 MTU >1280）——与 1280 内层 MTU 判据（QUIC DATAGRAM 头寸预算）冲突，
     须走判据变更 + 全链重验。
4. **判定**：在本设备（OHOS VPN fd + 内核 UDP 栈）与现设计（1280 内层 MTU / 每包 1 次 TUN write /
   DATAGRAM 逐包投递）下，**0.95× 结构性不可及**；本批已把**客户端侧可动的份额**（读面、回程跳数、热路径分配）
   全部取尽，剩余为设备内核与承载结构约束 ⇒ **交 M7 决策**（接受差异并登记 / 待设备侧能力 / 另开承载结构批）。

## 12.7.4 C：饱和（速率档） vs 真多做 —— **分离结论**

1. **同栈跨档**（最强证据，无跨臂混淆）：OLD 自然档 51.3/51.3/56.0 µs/单元（15.8–18.4k 包/s）
   → OLD **服务端限速 11 MB/s** 档 **93.3/97.9** µs/单元（8.8k 包/s）⇒ **+1.8×**。
   **同一份二进制、同一内核、同一会话**，只是速率档不同。
2. **同速率跨栈**：OLD@8.8k = **93.3/97.9** vs NEW@7.3–8.8k = **93.3/93.3/88.6/93.3/97.9**
   ⇒ **比值 1.00×（±5%）**。
3. **分离占比**：M6.5 报的 2.23×（M6 口径）/1.45–1.91×（M6.5 口径）里，**速率档项 ≈100%**；
   「真多做」（同速率下的结构差）**≤5%**（每单元总 CPU 93.3–97.9 vs 88.6–97.9，方向新臂略省；叶子和上新臂低 15–16 µs/单元，但该列带 ±25% 系统偏差）。
   ⇒ 用户质疑的核心判断（「大头和 quic/wg 关系不大」）**成立**。
4. **机制读数（速率档如何变成 per-call 成本）**：
   - 设备侧**核占空恒 ≈0.7–1.0 核/秒**，与速率无关（OLD 自然 0.92–1.38 / OLD 限速 0.92–0.97 /
     NEW 自然 0.68–0.88 / NEW 限速 6MB/s 0.75）；逐线程同（岛 0.32–0.41 在 9.1 与 6.0 MB/s 两档
     几乎相同）。
   - ⇒ **每单元 CPU ≈ a + b/速率**（两档拟合 OLD：a≈3.5 µs、b≈0.79 s/秒 ⇒ 即「不随速率变的
     ~0.79 核/秒」项主导）。速率减半 ⇒ **每单元 CPU 翻倍**（与实测 1.8× 一致）。
   - **每轮包数**（每 pass 处理多少包）随档位 159–185 → 26–29 → 5.8–6.3；**每 syscall 成本**随之
     16 → 29 → 34–35 µs（TUN write）/ 11 → 18 → 20–22（UDP recv）⇒ 「同接口不同代价」= **pass 粒度/
     速率档**，不是栈。
5. **对 M6.5 的「反常识」的正面解释**：新臂「单是系统调用 91 µs/单元」> 旧臂「整条 49 µs/单元」
   ——因为新臂运行在**低速率档**（8.5k 包/s），旧臂在**高速率档**（16–18k 包/s）；把旧臂**人为限到
   同一速率档**，它的整条流水线**同样**变成 93–98 µs/单元。**反常消失，归因不成立。**

## 12.7.6 对「0.95× 结构性不可及」的处置：**订正**

- **维持的部分**：M6.5 §12.4 的三条「结构性前提」（内核 UDP 真批化 / 非逐包 TUN 写 / 增大内层 MTU）

- **订正的部分（核心）**：M6.5 的**归因链**（「系统调用面占 81% 且其中 TUN/UDP 是本设备同内核的

  1. 两臂同付这些系统调用（旧臂 1.000 TUN write + 1.005 UDP recv/单元，**且无批化**）；

- **新结论（不粉饰）**：**本批未证「0.95× 结构性不可及」**。已证的是：**本核数据面的 syscall
  结构不是不可及的来源**（同速率等价，且新臂叶子更省）；不可及与否取决于**速率档能否抬起来**
  （~8.5k → ~16k 包/s，或把「不随速率变的 ~0.8 核/秒」降下来）。
- **判据现状**：T2 = 0.484×（判据 ≥0.95×）⇒ **仍不达标**；T6 = 1.82×（判据 ≤1.10×）⇒ **仍不达标**。

## 12.8.0 结论摘要（**不粉饰**）

| 维 | 结论 |
|---|---|
| **根因（已定位到环 + 已复现闭环）** | **岛侧 UDP socket 的**内核接收缓冲**在突发下溢出**（真机 `/proc/net/udp` 的 socket `drops` + `/proc/net/snmp` 的 `Udp: RcvbufErrors` 同源逐轮 +17…+32）。QUIC **DATAGRAM 不重传** ⇒ 每个被内核丢掉的报文 = 内层 TCP 的一次**丢段**（对端 dup ACK / RTO），而**出口侧 quinn 的 `lost/congestion_events` 也逐轮增长（24/7）**、cwnd 被 CUBIC 反复砍在 150–450KB ⇒ 下行只能以「突发 + 空转」的形态推进（每秒粒度实测：空转 1–2 s 与 17k 包/s 突发交替）⇒ 平均包率腰斩。 |

## 12.8.3 STREAM vs DATAGRAM 逐环比对（**任务 §2.A-5**）
