## 必答①：多 peer device 的线程所有权与锁面

**结论：单驱动线程独占全部可变状态的决议正确**，与 R1「自管线程 + poll(2) 三唤醒源」
一致，也满足 R1 三条死锁纪律的方向。Go 侧 `opCh`/`applyDeviceOpAsync` 的消除论证经实读成立
（`pkg/servercore/peers.go:147-154` 注释：IpcSet 拿 device 内部锁，ReceiveFunc 里同步等会与
device.Close 收工互为死锁环——自建 device 无此结构）。**但锁面清单不完整、驱动线程有阻塞点、
worker 模型有线程爆炸与不可中断阻塞**，见 H3/H4/H5/M9/M14。

## 必答②：漫游跟随的端点更新路径与 reg 的关系

**Go 真源口径复核：设计 §2 的四条主线正确**——init 成功 → 更新（`:374`）、response 成功 → 更新
（`:401`）、data 认证成功 → 更新（`:459/:515`）、**reg 与 endpoint 无关**（`ipc.go:32-35` 的
AddPeer UAPI 无 endpoint 键；`bind.go:685-690/733-736` 的 reg 只调 `Table.Register`）。
「新源首包日志按 src 去重 + 4096 满清表」也对（`bind.go:783-800`，`srcSeenMax=4096` bind.go:127）。

**但判据与两处细节要订正**：
1. **判据不能按 `TunnResult` 判「认证成功」**：R1 强制的「空数据报重调」返回 `Done`
   （`mod.rs:286-288`）、cookie reply 也返回 `Done`（`mod.rs:375-391`），二者都不是
   「认证成功的 peer 包」；wireguard-go 对 cookie reply 不更新 endpoint。见 **M2**。
2. **更新必须先于应答发送**：wireguard-go 是 `SetEndpointFromPacket`（`:374`）在前、
   `SendHandshakeResponse`（`:381`）在后。设计只写了「更新时机」，没写与发送的顺序（M2 附）。
3. Go 的 endpoint 更新与 allowedips 拒绝**不互斥**（`:515` 先记 `validTailPacket` 再查 allowedips）；
   Rust 按「非 Err 才更新」会把「认证成功但内层源不合法」排除在更新之外（终态差异极小，登记即可，低）。

**reg 面**：`reg` 只进设备表 ✓；hint（type=1）的 src 校验归装配层 ✓（Go 由
`relayclient.go:77-92` 校验「src 必须是中继」——R3 无中继腿时装配层应显式不装钩子，
钩子注释说明来源校验义务 ✓ 设计已写）。

## 必答③：UDP 长会话的 pending 重放窗口语义

**逐条核对通过（四题中对齐最好的一题）**：

| Go 真源 | 设计 | 判定 |
|---|---|---|
| `key = src:port→dst:port`，`udpSess[key]=true` **同步置位在 spawn 前**（`intercept.go:436, 460-465`） | 「置在建位」在驱动线程同步 | ✓ |
| 在建窗口重复包入 `udpPend`，`len(pend) < 16` 才 append = **丢最新**（`intercept.go:444-451`） | ≤16 丢最新 | ✓ |
| 上限 `MaxUDPSessions=4096`（`intercept.go:452-459`，`serve.go` 未覆盖默认） | 4096 | ✓ |
| `takePending` 取走并清空，**first 先于 pending**（`intercept.go:545-554`） | 顺序论证（first 是 worker 首写，pending 随后 FIFO）成立 | ✓ |
| 失败路径 `dropUDP` 清两表，后续同五元组重新走新会话（`intercept.go:463, 478-483`） | Teardown → 清两表 | ✓ |
| DNS :53 走进程内腿、idle 10s、不计 dialok/dialfail（`intercept.go:488-543`，`dnsleg.go`） | 同 | ✓ |
| `downSeen` 只在 real→peer 写成功后置位，只 transit 会话上报（`intercept.go:587-589, 633-639`） | 同 | ✓ |
| idle 60s（DNS 10s）+ 共享活跃时间戳 + 节拍 `min(readSlice, idle/3)` 下限 20ms（`intercept.go:601-627`） | `min(idle/3, 30s)` 下限 20ms | ✓ |

**唯一要补**：窗口边界写成「首包 → `UdpReady` 回到驱动线程」，必须同时规定
「重放走 upstream 直投、**不再注入拦截栈**」（否则同一包会双投）；以及 Go 的
「端点注册后同五元组不再进 handler」在 Rust 无 demux，需要靠「映射存在即直投 upstream」
等价实现——设计语义对，但这句话要显式写死，防止实现成「映射存在则注入栈」。

## 必答④：拦截层与 LocalServices UDS 的组装边界（NAT 重写 vs gVisor Forwarder+spoofing）

**方案方向正确**：实读 smoltcp 0.11 确认无 promiscuous/spoofing/任意端口动态 accept 面
（`iface/interface/ipv4.rs:107-122` 目的地址非本机即丢；`socket/tcp.rs::accepts` 要求
listen endpoint 或四元组精确匹配；`socket/udp.rs` 只有 bind/send/recv）。用户态 NAT
重写（REDIRECT）是标准替代，**不是 Go 直译**，符合工程原则。

**但「语义等价」不成立，有 5 处客户端可观察差异**（§4.2 差异表须补行并逐条判「等价/有意登记」）：

| 面 | Go（真源行） | 设计现状 | 客户端可观察后果 |
|---|---|---|---|
| **TCP 建连时序** | 先拨 upstream（10s 预算）成功后才 `CreateEndpoint`（`intercept.go:334-371`）；期间 SYN 被 Forwarder 的 inFlight 吞掉（`forwarder.go:78-90`），失败 → `Complete(true)` → RST → 客户端 `connect()` 直接 refused | 先 listen 再 spawn worker 拨号 → **立即 SYN-ACK** | 拨号慢/黑洞/拒绝三态全变：refused → established-then-hang/RST（**H2**） |
| **通告接收窗口** | Forwarder `rcvWnd=4096` 直接作为端点接收缓冲/SYN-ACK 窗口（`intercept.go:181`；gVisor `accept.go:77-79, 205`） | 未定（客户端 StackB 是 `TCP_BUF=1MB`，`stackb.rs:32`） | 窗口差最高 256×，吞吐/长肥管道行为完全不同（**M-RWIN**，§4.2 只对了 MSS/SACK/Nagle） |
| **UDP 无端点** | gVisor 回 ICMP port unreachable | smoltcp `process_udp` 无匹配即静默（设计只做了「会话表满」的 ICMP） | 应用超时 vs 快速失败（L3） |
| **未知四元组非 SYN** | gVisor `HandleUnknownDestinationPacket` **回 RST**（`protocol.go:166-181`） | 设计「丢」 | 客户端 stray ACK/FIN 无 RST（L4） |
| **UDP 会话端点** | `dialUDPShared` 用 SO_REUSEADDR/PORT 绑**原目的地址**+Connect 原源（`intercept.go:653-671`） | 「bind 拦截栈地址:rw_port + connect 客户端源」——**smoltcp UDP 无 connect API**，且共享语义被 rw_port 唯一化（简化正确） | 需以「唯一 rw_port + 读时校验 UdpMetadata 源」替代 connect（**M11b**） |

**另外必须钉死的前提**：设计依赖「smoltcp IP 层丢弃 dst≠本机地址」，这只在
`any_ip=false` 时成立（`iface/interface/mod.rs:223` 默认 false，但 `set_any_ip` 是公开 API，
:369）。建议在 §4.1 写明「不得开 any_ip」并加一条断言单测。

**LocalServices 边界核对（无问题）**：只 TCP 豁免查表（`intercept.go:338-345`，UDP 不查）；
命中但拨号失败**不回退** 127.0.0.1（同 :343-345）→ RST；条目建后不改、ENOENT 快速失败；
`listenLocalService` 死/活判别 200ms 拨号 + chmod 0600 + identity 删残留 + 路径 <100B
（`serve.go:577-627`）；term 不起就不建 term.sock（Go `term.Disabled()` 同口径）✓。
拦截常量也对：`MaxConns=1024`/`TCPIdle=5min`（serve.go:344-345 覆盖包内默认 4096/6min）、
`UDPIdle=60s`/`DNS 10s`/`udpPendingMax=16`/`MaxUDPSessions=4096`/拨号 10s ✓。

## 问题清单（位置 / 问题 / 建议 / 严重程度）

### 高

**H1. bind 分发漏掉容器帧（type=4），Go 客户端首包注册路径不存在**
- 位置：设计 §1.1（腿帧分发只列 data/reg/control）、§5 3a；真源 `pkg/servercore/bind.go:672-719, 721-760`、`pkg/proto/frame.go:27`。
- 问题：Go 客户端首个握手数据报是 `[0xBB][4]{[2][len][reg][0][len][wg-init]}` 容器（R1-design §3 关键互通点 #2/#4；Rust `wtransport/bind.rs:261-290` 就是这么发的）。设计的 bind 只处理 data/reg/control，容器帧会落进「未知/非帧」分支被丢——**reg 与 init 都进不了 device，Go 客户端永远挂不上**，3a 判据直接红。另 `type≥3`（中继控制帧）Go 也走「noteNewSrc + 忽略」的可容忍路径（bind.go:701-707），设计未写。
- 建议：把 `decode_batch`（R2 已有，`frame.rs:103-143`）纳入分发，严格照 Go 顺序：reg 先登记 → data 只取首条投 device → control→hint → 未知忽略；补齐 shape 串全表（`腿帧数据/腿帧注册/腿帧控制/容器数据/容器（无数据）/畸形腿帧/畸形容器/参照点探测/STUN应答/非帧（%s，首字节=0x%02x）/腿帧type=%d`，bind.go:647-718, 763-775）与「入站新源表满」行（bind.go:795）。3a 加容器帧单测（[reg][init] 必须登记后投递）。
- 严重程度：**高**

**H2. NAT 路径的 TCP 建连时序与 Go 不等价（SYN-ACK 早于 upstream 拨号；失败语义从 refused 变 established→RST）**
- 位置：设计 §4.1 RX 分支（「栈上 listen…spawn worker 拨号」）；真源 `pkg/intercept/intercept.go:317-390`（拨号在 `CreateEndpoint` 之前）、gVisor `forwarder.go:78-90`（inFlight 吞重复 SYN）。
- 问题：Go 语义 = 「upstream 通了才回 SYN-ACK；拨号失败回 RST（应用见 connection refused）；拨号期间客户端 SYN 重传被静默吞」。设计 = 「立刻 listen 回 SYN-ACK，拨号在后台」。三条客户端可观察差异：连接建立时点、失败可见性（connect 成功但读到 RST/挂死）、拨号黑洞时 10s 的行为。
- 建议：TCP 也走「pending 建连窗口」——SYN 先只建映射、**不注入栈**（重传 SYN 在窗口内继续吞），worker 拨号成功回 `TcpReady` 后由驱动线程建 socket+listen 再注入 SYN（smoltcp 回 SYN-ACK）；拨号失败由驱动线程构造 RST（源 = orig_dst，走 encap 直发，和 ICMP responder 同一手法）或注入后立即 abort。把 E10「dialok」的产出语义钉为「SYN-ACK 已回 + upstream 已通」。
- 严重程度：**高**

**H3. DNS 代答可能跑在驱动线程上（阻塞最长 2.5s/查询），违反死锁纪律 #2**
- 位置：设计 §1.1（线程模型只列驱动线程 + 拦截 worker）、§3 DNS 特判、§5 3d；真源 `pkg/dns/server.go:64-74, 198-234, 266, 357-388`（goroutine + 256 in-flight + 每查询新 socket + resolv 跟随）。
- 问题：DNS 上游查询是阻塞 IO（budget 2500ms、每 nameserver 800ms 切片、失败兜底 223.5.5.5）。驱动线程若直接调 `Answer()`，一条上游黑洞查询就把 WG 数据面（含 keepalive/握手重传/其它 peer）卡 2.5s；256 并发在飞时更糟。设计没写 DNS 的线程归属。
- 建议：DNS 查询交专用 worker（固定 N 条 + 有界队列，满则按 Go 的 drop 计数），驱动线程只做「从栈内 listener 读查询 → 投队列」与「收应答 → 写回栈内 socket」。
- 严重程度：**高**

**H4. worker 模型「每流一条 OS 线程」= goroutine 直译，且消息面不完整**
- 位置：设计 §1.1（「拦截 worker 线程（每过境 TCP 连接/UDP 会话 1 条，小栈 256KB）」）；对照 Go 的 goroutine 模型（每 UDP 会话 3 goroutine，intercept.go:628-631）。
- 问题：(a) 上限 1024 TCP + 4096 UDP = 5000+ OS 线程 × 256KB ≈ 1.25GB 虚拟栈 + 调度开销（Go 的 goroutine 近零成本）——这正是 AGENTS 工程原则 5 点名的「Go 直译痕迹」；(b) 消息枚举只有 `TunnelWrite/ToUpstream/Teardown`，缺 worker→驱动的「upstream EOF/错误」、驱动→worker 的「半关/客户端 FIN」、connected-UDP 的 ICMP-refused，实现时必然临时扩展。
- 建议：改固定小池（2–4 条）poll(2) 多路复用所有 flow（与驱动线程同一套自管线程习惯，不引 async），或至少写死「线程上限 + 满则拒流/排队 + 压测」；消息面定成 `FlowCmd{Data|Close|Teardown}` + `FlowEvent{Data|Eof|Reset|DialFail|Ready}` 显式枚举（对齐 Go bridgeConns 的「首 EOF 双向拆、无半关」语义）。
- 严重程度：**高**

### 中

**M1. pending-init 表基于错误事实（type=2/3 的 receiver_idx 就在本端 base 空间），三表可简化成两表**
- 位置：设计 §1.2 表 3；实读 `handshake.rs:572-575, 659-661, 705`、`mod.rs:819`。
- 问题：response 的 receiver_idx = 我们 init 用的 local_index = `(base<<8)+k`；cookie reply 的 receiver_idx = `cookies.index` = 同一个 local_index。四类包（init 除外）都能用 `receiver_idx>>8` 命中 base 表。pending-init 表是冗余状态（rotate/expire/rebuild 多一处清理面），而且给实现者一个错误心智模型。
- 建议：删表（或降级为断言/诊断计数器）；3a 单测对 type=2/3/4 三类逐一验证 base 分派。
- 严重程度：中

**M2. endpoint 更新判据的两个 `Done` 陷阱 + 更新/发送顺序未写**
- 位置：设计 §2「更新时机」；实读 `noise/mod.rs:286-288`（空包重调 → Done）、`:375-391`（cookie reply → Done）、wireguard-go `receive.go:374→381`。
- 问题：按「非 Err 且类型 ∈ {…}」判，实现者若按 `TunnResult` 落地会把**空数据报重调**与**cookie reply** 误判为认证包更新 endpoint（后者是攻击者可控来源面的潜在污染）。另未规定「先更新 endpoint 再发送应答包」，顺序错会让握手响应发回旧地址。
- 建议：分派结果用显式枚举承载（`Init/Response/Data{authenticated}/CookieReply/Queued`），endpoint 更新只由 `Init|Response|Data` 触发，且声明「更新先于该次 WriteToNetwork 的发送」。
- 严重程度：中

**M3. `ConnectionExpired` → 原地重建 Tunn（换 base）与 Go 不等价且无必要**
- 位置：设计 §1.2 错误面、§1.3；实读 `timers.rs:195-197, 208-213`、`mod.rs:446-448`、`handshake.rs:482-564`。
- 问题：(a) Tunn 能自愈——入站 init 或出站 encapsulate 都会把状态从 Expired 带走，base 不变、排队包不丢；重建换 base 会让客户端发往旧 base 的在途数据包全部丢弃（Go 的 peer index 稳定）。(b) `session_established` 初值 0，注册后从未握手的 peer 在 540s 后被 `REJECT_AFTER_TIME*3` 判过期（timers.rs:208），设计会让这些空闲 peer 每 9 分钟被无谓重建一次（新 base、三表重登记）。
- 建议：Expired 只做「一次性清标志 + 抑制重复日志」（R1 的 `expired_pending` 同款），**base 永不变**（仅 rotate/remove 时销毁）。
- 严重程度：中

**M4. 「服务端不主动发 init」口径不成立（KEEPALIVE+REKEY_TIMEOUT 与 keepalive 路径都会起握手）**
- 位置：设计 §1.2（pending 表承认会发 init）与 §1.3（「responder 不主动 rekey…不主动重试」）自相矛盾；实读 `timers.rs:271-277, 307-309`。
- 问题：出口在「发过数据且 15s 无回」时会强制发起握手，keepalive 路径在无会话时也会 `encapsulate(&[])` 排队并发 init。这不是例外而是常态（例如 speedtest 下行结束、客户端静默后）。
- 建议：§1.3 改写为「服务端可发起握手（两条触发路径），走与客户端相同的 5s 重传/90s 放弃语义」；3a 加「服务端发起握手」用例（客户端静默 15s → 出口发 init → 客户端应答 → 会话建立）。
- 严重程度：中

**M5. `rate_limiter` 参数未定（客户端有「必须 None」硬约束，服务端需相反决策）**
- 位置：设计全文未提；R1-design §2（客户端必须 `None`）；实读 `rate_limiter.rs:111-113, 161-189`、`timers.rs:69, 174-176`。
- 问题：`Some(Arc)` 共享 = 全设备 10 握手包/s 计数（比 Go per-IP 20/s 更糟，多设备启动风暴下会互相触发 cookie reply）；`None` = per-Tunn 私有计数 + 每拍可复位（≈不触发）。无论选哪个，cookie reply 必须经 send 路径回源、且**不触发 endpoint 更新**；设计对 cookie reply 只字未提。
- 建议：明确 `None`（并接受 cookie-reply 路径）或自建 per-IP limiter；3a 加「>10 握手包/s → 出口回 cookie reply → 客户端带 mac2 重试」用例。
- 严重程度：中

**M6. 缺 R2 式「常量映射表」——对齐完整性无从评审**
- 位置：设计 §3/§4/§5 只有功能清单。
- 问题：拦截（1024/5min/60s/10s/4096/16，拒绝行在册数 = conns+1，intercept.go:309-310）、DNS（2500ms/800ms/256/64/30s/1232/60s/223.5.5.5/过滤 AAAA+HTTPS+SVCB+ANY/无缓存无 EDNS/仅连接层失败才兜底）、files（512KB/8MB/16MB/256KB/64KB/16 并发/5min idle/24h .tierpart/无 fsync）、speedtest（12 并发/30s/5s/15s/65535；**serve.go:515 注释「≤8」与代码默认 12 不一致**）、egress/UPnP（10min/2min/40s/30s/8s/5s/200 条/租期 3600→0 永久）都没有落表。
- 建议：照 R2-design 补一节「常量映射表」，每行给判据行 ID + 真源 file:line + Rust 落点/是否判据行。
- 严重程度：中

**M7. R2 移交微项没有清单（只写了「R2 移交微项」一句）**
- 位置：设计 §5 3f；真源 `docs/reviews/R2.md:62-72`。
- 问题：R2 明确挂 R3 的有：低-7 残余字符串错误载荷收窄（`FilesError::Transport`/`ActionError::Failed`/`DialError::Stack`）、低-10 smoltcp `set_timeout` 精确 idle 回收、低-5/6/8/12/16（last_punch Cell、punch 甩线程、bind 直连关语义死分支、endpointcache 手抄 struct、suspend_gap 内联 + maxTCPFlows 校验）。设计没逐条落步。
- 建议：逐条写「在哪一步做/不做+理由」；`set_timeout`（smoltcp `socket/tcp.rs:612` 有）与 R3 socket 生命周期天然同处，纳入 3c。
- 严重程度：中

**M8. 缺背压设计：无界通道 + 无读门控 → smoltcp 缓冲被抽干、客户端窗口恒开、内存无界**
- 位置：设计 §1.1（unbounded 通道 + 三条纪律）。
- 问题：Go 的 bridge 阻塞在 upstream write 会经 netstack 端点缓冲反压到客户端窗口；Rust 若驱动线程无脑读栈内 socket 投 `ToUpstream`，慢 upstream（挂住的 TCP）会让队列无界增长且窗口不再收紧。
- 建议：把「无界通道 + 高水位读门控（如每流 ≥256KB 或 ≥64 包则本轮不读该 socket，把数据留在栈内让窗口关）」写成纪律第 4 条；双向（worker→driver 同样门控写栈）。
- 严重程度：中

**M9. worker 侧 socket 所有权与 Drain 的 RST 语义不闭合**
- 位置：设计 §4.1（「到期 RST——`TcpStream::set_linger(Some(0))`」）。
- 问题：upstream socket 归 worker，驱动线程不能直接 `set_linger/close`（与 worker 阻塞 read 竞争）；worker 若无读超时，Teardown 要等下一次数据到达才生效（Go 是 30s readSlice + `SetLinger(0)` 直接 close 唤醒，`intercept.go:225, 703-720`）。
- 建议：worker socket 设 `set_read_timeout`（对齐 30s 切片）或 worker 也走 poll(2) + self-pipe；明确「Teardown = 驱动投递 → worker 收到后 set_linger(0)+close 并回执」的所有权转移。
- 严重程度：中

**M10. 出口 v6/双栈面缺失且未登记**
- 位置：设计全文；对照 Go `servercore/bind.go:517-527`（`net.ListenUDP("udp")` 双栈）、`receive.go`/`intercept` 的 v6 分支。
- 问题：Rust 客户端 Bind 已登记「v4-only，v6 挂真机前补」；出口设计同样没有双栈/端点族口径（token 可含 v6 端点、Go 客户端可带 v6 直连端点）。
- 建议：显式登记「R3 出口 v4-only（v6 承载/端点/token 条目挂 R7 真机前）」，并说明本地纯 v4 矩阵下无差异。
- 严重程度：中

**M11. 映射生命周期状态机缺失（TIME_WAIT / rw_port 复用 / UDP 无 connect / 关流竞态）**
- 位置：设计 §4.1 TX 反查与 §3 UDP；实读 smoltcp `socket/udp.rs`（无 connect）、R1-design §4（③-8 socket 留到 Closed）。
- 问题：(a) smoltcp TCP socket 进 TIME_WAIT 期间若映射已删，客户端最后 ACK/FIN 重传失去映射（Go 端点仍在 TIME_WAIT 接包）；(b) 「bind+connect 客户端源」是 smoltcp API 事实错误，需「唯一 rw_port + 读时校验 UdpMetadata 源」；(c) rw_port 何时可复用未定。
- 建议：写一节「映射状态机 New→Listening→Established→Closing→TimeWait→Reaped」，每态给出收包处置与 Go 对照行；明确 rw_port 在 socket `state()==Closed` 后才释放。
- 严重程度：中

**M12. 栈内 socket 选项面（R2 低-10 的接手点）没写**
- 位置：设计 §4.1；真源 `stackb.rs:209-227`（只设 Nagle off）。
- 问题：出口 idle 5min 若只靠驱动拍检查，socket 会长期占 SocketSet；smoltcp 有 `set_timeout/set_keep_alive/set_ack_delay`（`socket/tcp.rs:612, 619, 658`）可用。
- 建议：在设计里定「idle = 驱动拍检查 + set_timeout 双保险」并说明与 Go `SetReadDeadline(readSlice)`+watchdog 的对应关系。
- 严重程度：中

**M13. HaltNew/Drain 的收口顺序与语义未写全**
- 位置：设计 §4.1 一句话；真源 `serve.go:638-689`、`intercept.go:319-324, 428-435`。
- 问题：Go 的 Shutdown 顺序 = HaltNew → 关三 UDS listener（identity 删残留）→ Drain(grace)（自然收/RST/2s 销账）→ dev.Close → relayCancel/dns.Close/shrinkUPnP → 各服务 Close → closeLogs；且 HaltNew 后**新 TCP SYN 回 RST、新 UDP 首包回 ICMP 且无日志**。
- 建议：把完整顺序与两条「停新流」语义写进 3f；Drain 的「registry 空则立即返回、不等宽限」细节（intercept.go:213-216）也照抄。
- 严重程度：中

**M14. 共享状态×线程×锁清单不完整；吊销跟随语义缺失**
- 位置：设计 §1.1（只列 table 快照 Mutex）。
- 问题：还缺 token/revoked 台账（装配/公网端点线程写、驱动线程 Register 读）、revoked.jsonl 的 1s mtime 跟随读（Go `revoked.go:27`，吊销对新注册秒级生效、无需重启、**不拆已在表设备**）、日志双通道（summary/detail 分口）、CLI stop/self-pipe、worker 两侧通道、UDS 服务与 DNS worker 线程。
- 建议：补一张「状态 × 属主线程 × 同步原语」表；明确吊销只影响新注册，已在表设备走 TTL/rotate/删表。
- 严重程度：中

**M15. 判据行覆盖清单不全**
- 位置：设计 §5（只点 E4-E14/E17/E18/E20/E22/E23）。
- 问题：缺 E1/E2/E3（serve 装配 + token 打印，E3 有「端点已变化」变体）、E19（后端身份）、E21（绑卡：自动挑到——设计保留启动期一次挑卡，这一行在范围内）。E16/E15 属 term（排除 ✓）。

## 总体结论

**设计方向可作为 R3 实现基线，但 v1 不能直接开工**：

1. **必须先整改（高）**：H1（容器帧——否则 3a 第一步就红）、H2（TCP 建连时序/拨号失败语义）、
   H3（DNS 不得在驱动线程阻塞）、H4（worker 线程模型与消息面）。
2. **建议同批整改（中，低成本高收益）**：M1（删 pending-init 表）、M2（endpoint 更新判据）、
   M3（不重建 Tunn）、M5（rate_limiter 定 None + cookie reply 路径）、M6（常量映射表）、
   M7（R2 移交清单）、M8（背压门控）、M11（映射生命周期状态机）、M14（锁/共享状态表）。
3. **可登记后置**：M10（v4-only）、M12/M13（并入 3c/3f）、M15（判据矩阵）、全部低项。
4. **拆步可并行**：3b（设备表/state）与 H1/H2 的整改互不依赖，可在设计 v2 定稿同期先行；
   3c（拦截）必须等 H2/M11 定稿；3a 必须等 H1。
5. **验收锚提醒**：H2 与 M-RWIN（Go Forwarder `rcvWnd=4096` 的通告窗口）会直接影响
   speedtest/files 的 A/B 读数——建议在设计 v2 里先定「拦截路径接收缓冲 = 4096（对齐）
   还是有意放宽+登记」，否则 ±50% 判据的锚点会漂。
