## 1. S1′：**本批不新增令牌桶**，改用仓内既有出口侧字节令牌桶（偏离任务书 S1 字面设计，**开工前登记**）

**偏离结论**：不按字面在 `crates/homeway-quic/src/exit/**` 的下行 DATAGRAM 注入点新增第二个令牌桶；
实验旋钮 = **既有** `Interceptor::pump()` 尾的字节令牌桶（`TxShape`）：

| 面 | 既有形态 | 出处 |
|---|---|---|
| 速率 | env `HOMEWAY_TX_RATE_MBPS`（**MiB/s**，`n × 1.048576e6 B/s`）/ config `[serve.tx_shape] rate_mbps` | `homeway-core/src/server/intercept/mod.rs:422` `tx_shape_resolve` |
| 突发 | env `HOMEWAY_TX_BURST_KB`（KiB，缺省 256）/ config `burst_kb`；桶容量 = 单拍放行上界（同值） | 同上 + `shape_slice`（:477） |
| 逃生口 | `HOMEWAY_TX_SHAPING=off`（值匹配） | 同上 |
| 默认 | **开**，rate=**200 MiB/s** / burst=**256 KiB** ⇒ 即本批「0 档/现状」 | `TX_SHAPE_RATE`/`TX_SHAPE_BURST`（:356/:362） |
| 生效值读回 | 启动行 `intercept: 发送整形=开（rate=…MiB/s burst=…KiB；…）` | 实测例：`rate=33MiB/s burst=256KiB` |
| 计数行 | 5s 行 `intercept: 整形观测 滞留=…包/…KB 峰值=…包/…KB 窗释=…(均…包/拍)` | `cc_stats_line`（:1904） |
| 超限策略 | **滞留 FIFO（有界）+ 下拍续传**：TCP 面**恒不丢**（队列深度由 Σcwnd 自然钳制）；非 TCP 并入超 4 MiB（`TX_DEFER_MAX_BYTES` = 16×burst）才丢新 + `shape_drop` 计数 | `tx_shape_release`（:1802）/ `filter_defer`（:1782） |
| 单测 | 桶算法/边界/保序/极小 burst 直通 = `shape_slice_budget_and_continuation`；参数解析表 = `tx_shape_resolve_config_table`；关档等价 = `pump_hold_defers_without_double_accounting` / `wait_hint_states`（`tx_shape=None` 恒直通） | `homeway-core` 单测（本批 `cargo test --workspace` 全绿复跑） |

**理由（四条，逐条带证据；任务书 §1「有更优设计要在回报里说明理由」）**：

1. **覆盖等价（零新增覆盖）**：出口侧 DATAGRAM 的**唯一**生产写入点 = `engine.rs:1647` 的 `route_out`，
   其入参 = `intercept.pump()` 的返回（`engine.rs:1387`）——**即已过令牌桶的释放集**。
   在 QUIC 注入点再挂一个桶，相对既有桶**不覆盖任何新增字节**（STREAM 面不是 DATAGRAM；plain 面不是设备流量）。
2. **语义更安全**：既有桶对 TCP 面恒不丢包、队深自然有界（≤ Σcwnd）；注入点新桶要么无自然上界
   （缓冲账不可封、与 8192 条出站队列叠加），要么丢包——后者正是仓内 R8-3 已裁定的「整形器丢包 = 伪修复禁区」
   （`docs/reviews/R8.md` §九）。真机数据也支持：本批整形档滞留在稳态**≈0**（见 §3），零排队延迟代价。
3. **红线**：`crates/homeway-core/src/server/intercept/**` 属本批红线（任务书 §2「不动」）⇒ 既有机制只能**原样用**，
   其观测缺口（**非法 env 值静默回落**，doc 注释自认「非法值静默回落默认」）本批**如实登记、不修**。
4. **零产品改动 = 最强形态「默认关/零风险」**：不设 env ⇒ 一个字节不变（收口后 `target/release/homeway-cli`
   与批前同 sha256 前 16 = `e4a5fc66f48d1bfc`）；无新队列/新定时器/新内存账。

**代价（如实）**：既有桶的速率语义是「**削峰不平率**」（R8.md §九：「R 的职责 = 团块钳制，不是速率限制」），
故本批测的是**该桶的下限方向**（把 R 压到空口锚附近），不是「注入点精确控速」；两者在**本条链路上**（§1-1 的覆盖等价）
行为面相同。若主会话/用户仍要 QUIC 注入点的**独立**旋钮，须先回答「与既有桶的关系」（串联/取代/双旋钮语义）。

## 5. 结论（本批）

1. **能不能把 T2 抬到 ≥0.95×？**——**本会话不可判**：P33/P41 对 P0 的同会话比值 1.131×/1.052× 落在
   逐轮噪声（1.71× 极差 + 会话单调退化）内；且本会话**未复现** M6.7 的强丢形态（P0 峰值 1.06× 锚 vs M6.7
   的 1.05–1.32×、P0 丢轮 2/8 vs M6.7 的逐轮 lost 64–79）。**绝对档登记**：P0 热中位 15.09 MB/s（同会话），
   与 §9.20.11/§9.20.12 的 cubic 带（19.7–20.1 MB/s，跨会话）不可互引。
2. **代价**：速率档下**稳态零排队**（滞留≈0）⇒ 无延迟/内存/体积代价（**零代码改动**）；
   burst 档（未测）预计有代价（R8-3 梯度）。
3. **留/不留**：**不改默认档**（默认 200 MiB/s 一个字节不变）；既有旋钮 `HOMEWAY_TX_RATE_MBPS`/`_BURST_KB`
   已具「可调 + 可观测 + 可退出」，**本批不新增旋钮、不新增机制**。若用户要产品面「按带宽整形」，
   下一批的动作 = 调**既有** `TX_SHAPE_RATE` 默认值（含 burst 面），本批数据支持「速率档 0.8–1.0× 锚**无害**」，
   但不支持「能补 11%」（本会话不可分）。
4. **下一个该试什么**（按本批数据的排序）：①**burst 档**（`HOMEWAY_TX_BURST_KB=32~64` + rate 0.8× 锚）——
   本批唯一未消掉的丢包面是**启动瞬态团块**（首 RTT 200–370 包，恰 = 256 KiB 缺省 burst），缩 burst 是对症臂；
   ②在**重丢会话**（M6.7 形态：P0 峰值 ≥1.1× 锚、逐轮 lost≥60）复跑 P33/P41——本批的「零增益」结论受限于
   会话未进入该形态；③若仍要打那 11%，靶子应回到**非速率面**（如岛侧回程队列 2048 包的丢面、内层 MTU）。

## 8. 方法学注记与如实登记（防后人误读）

1. **每轮 = 一次出口重启换档**（env 是进程级）⇒ 每轮都是**新外层 QUIC 连接**（`conn_id` 递增、cwnd 从
   `initial_window=12000` 起）+ **新内层 TCP 连接**（浏览器逐轮开新 URL）。本批「热」= App/隧道**进程**常驻
   （不 force-stop），**不是**连接常驻；「冷」= 前述 + force-stop + 30s 空闲 + 重注入。三档同规程 ⇒ 可比值同质。

   同会话比值**；跨会话绝对值（含 §9.20.11 的 20.14 MB/s 与 0.95× 目标带）**只登记不判**。
3. **两轮 MISS 作废**（labels `P0h06`/`P41h03`）：浏览器侧未起下载（预热失败 + 无下载框），非出口/隧道故障

4. **临时插桩的一处笔误**（不粉饰）：`qs[stat]` 行里的 `pkt_s` 字段打印的是 **`udp_tx` 累计值 ÷ dt**，不是

### 10.4 **判决 1（本批靶子）：启动团簇丢包 ★未消失、也未被 burst 界定★**

1. **clean 热 9 轮里，启动窗（0–1s）丢包只出现 2 次**：B256h01 = 31 包（+0.3 s，cwnd 11 K→610 K，
   当刻 3.2 K 包/s）与 B64h05 = 7 包（+0.6 s）。**B32 三轮全 0**。
   ⇒ 幅度上：**B256 31 > B64 7 > B32 0**（每点 n=3，**弱**），方向上与「小 burst 削启动峰」相容。
   但 clean 冷档里同样出现过 **B64Cc01 = 46 包（+0.9 s）**（B256Cc01/B32Cc01 = 0）⇒ 该「方向」在两批
   小样本里**不一致**，不能当结论。
2. **但「启动团簇」这个对象本身在本会话没有复现出 QS 假设的规模**：QS §5-4① 的「首 RTT 一次打出
   200–370 包」是**由缺省 burst 反推**、不是实测（§3 表里无此读数）。本批在**逐秒分辨率**上量到的
   首秒丢包上限 = **31 包**（B256），且 9 轮里 7 轮首秒零丢。**没有任何一轮出现「200 包级首秒丢包」**。
3. **真正反复出现的丢包在轮中段（+3.5~4.7 s），与 burst 无关**：B256h01 +4.5 s 24 包 / B64h01 +4.2 s 24 包 /
   B64h02 +4.7 s **412 包**（cwnd 1115 K→780 K、**当刻 RTT 254.8 ms**）/ B64h04 +3.5 s 24 包 /
   B256h05 +3.9 s 32 包。**本批最大丢包事件（412 包 = 516 KB）发生在 burst=64 KiB 档**——
   即「把 burst 压小 ⇒ 丢包集中消失」的因果在数据上不成立：**丢包 episode 的量级由会话/空口状态决定**。
4. **机制侧正面读数（小 burst 确实咬住，但咬住的是队列不是丢包）**：首窗 `整形观测` 峰值滞留
   **B32 692/745/724 包（≈860–932 KB）> B64 269/731/685 > B256 443–576 包**；稳态「均包/拍」
   **B32 18–20 / B64 19–26 / B256 33–46**，而拍率反向 **B32 800–999/s > B64 538–828 > B256 458–653/s**。
5. **一个反直觉的定量发现（登记，机制未取证）**：**首个 5 s 窗的释放量在 9 个 clean 轮里 7 轮落在
   8,933–8,980 包（11.2 MB，离散 ±0.3%）**，与 burst=256/64/32 无关（例外：B256h02 = 8,030、
   B64h05 = 2,768——两轮都是更慢的轮）。⇒ 启动爬坡的**限额不在整形器**（若在，`窗释` 应随 burst 变），
   而在上游（内层 TCP 慢起/浏览器落盘/服务端读侧——本批未取证）。

### 10.5 判决 2（吞吐）与判决 3（代价）

- **吞吐**：见 §10.3 中位与比值——**不可分**（B64 0.863×、B32 0.965×，逐轮极差 1.35× ≫ 臂间差；
  且 B64「最慢」在早晚两窗都出现，但每窗内只有 1–2 轮 ⇒ 无统计力）。
- **代价 A（档位余量，★可判定★）**：单拍放行上界 = burst/1252 B ⇒ **B32 = 26 包/拍、B64 = 52、B256 = 209**。
  实测拍率上限（本批 25 轮内最大）= **1,059 拍/s** ⇒ **B32 的算术上限 = 26 × 1059 = 27.5 K 包/s
  ≈ 档位上限 27,636 包/s（余量 ≈ 0）**；B64 = 52 × 828 = 43 K 包/s（**余量 ≈ 1.6×**）。
  ⇒ **burst=32 KiB 在 33 MiB/s 档位上是「零余量 / 边缘档」**：拍率任何下滑都会让 burst 先于 rate 咬住。
  反推缺省档自洽性：缺省 rate=200 MiB/s，1 ms 拍 ≈ 210 KB ≈ 缺省 burst 256 KiB（R8-3 的取值本就
  与「burst ≥ rate × ~1 ms」同构）。
- **代价 B（启动排队延迟）**：首窗峰值滞留 **B32 ≈ 860–932 KB**（B256 ≈ 555–718 KB）⇒ 按档位
  33 MiB/s 折算，**B32 的启动排队 ≈ 25–27 ms**（B256 ≈ 16–21 ms）——只在启动爬坡段存在（稳态
  `滞留=0`，与 QS §3 机制证据 2 一致：削峰不平率）。
- **代价 C（拍频/出口 CPU）**：B32 的拍率约为 B256 的 **1.8–2.2×**（800–999/s vs 458–653/s）⇒
  出口侧每拍固定成本（poll/记账/系统调用）同比升高。**本批无出口侧 CPU 仪器 ⇒ 登记为未取**
  （T6 是设备侧读数，见下）。
- **代价 D（设备侧 CPU = T6）**：中位 **B256 74.6 / B64 79.3 / B32 74.6 µs** ⇒ 比值 B64/B256 =
  **1.063×**、B32/B256 = **1.000×**，均在判据 ≤1.10× 内（登记级；**仪器量化 = 0.01 s CPU / 214,406 包
  = 46.6 µs/格**，故 74.6 三连相同是量化产物，不是「精确相等」）。
- **代价 E（岛侧核缓冲）**：设备 `Udp: RcvbufErrors` 逐轮差 **全 25 轮 = 0** ⇒ M6.7 修复状态保持；
  设备 `Tcp: RetransSegs` 逐轮差：clean 热轮 1–9（B256 1–3 / B64 8–9 / B32 2–5）、全 25 轮 0–30——量级与 QS 的重丢轮（28）同级但不成片。

### 10.6 结论（三问三答）

1. **启动团簇丢包是否消失？** **没有**——但**也不是被 burst 界定**：clean 热 9 轮首秒丢包上限 31 包
   （B256 1 轮）、B32 三轮零；而**量级最大的丢包（412 包）出现在 B64**，且全部大 episode 都在轮中段
   （+3.5~4.7 s）。**QS §5-4① 的「启动团簇 = 缺省 256 KiB burst 所致 ⇒ 缩 burst 是对症臂」被否**：
   缩 burst 让**队列**变大（860–932 KB）、峰值包率下移，但**没有让丢包面消失**。
2. **吞吐有无系统变化？** **不可分**（同会话比值 0.863× / 0.965×，均落在逐轮噪声 1.35× 内）。
3. **代价**：见 §10.5 —— 最硬的一条是 **B32 相对 33 MiB/s 档位零余量**（26 包/拍 × 实测最大拍率
   ≈ 档位上限），外加启动排队 +5~10 ms、拍频 ×1.8–2.2（出口 CPU 未取）。
4. **要不要写进部署建议？** **不建议把 burst=32/64 写进部署建议**（本批没有任何一项读数支持它有增益；
   32 还有零余量的结构性风险）。要写也只写**一条约束式建议**（若将来做窄带档）：
   **`burst_kb ≥ rate_mbps × 1.5`**（实测拍周期 ~1 ms ⇒ 1.5 ms 余量）——33 MiB/s 档 ⇒ **≥ 50 KiB
   ⇒ 64 KiB 是下限档**；缺省档无需动（200 MiB/s × 1.5 ms ≈ 315 KiB ≈ 现值 256 KiB 同量级）。
   **默认档一个字节不变**（本批零代码改动）。

### 10.8 方法学注记与如实登记（防后人误读）

1. **dirty/clean 二分是本批的前置**（§10.2）：若非事后取证（22:11 的浏览器会话恢复实验），
   dirty 轮的「+0.3~0.9 s 启动丢包」会被误读成「B32/B64 也有启动团簇」——**它其实是浏览器恢复
   产生的预轮传输**。**本批 6 个 dirty 轮（含 3 个冷档）的启动窗读数一律不用于启动判决**。
2. **Mac 环境 loadavg 基线远高于 QS 批**：本批 clean 热轮 loadavg 峰值 1.34–2.78（QS ≤1.89）；
   clean 冷轮**轮首 3.34 / 4.68 / 4.87、峰值 4.05 / 5.90 / 4.87**（dirty 冷轮只 2.22–2.69）。
   ⇒ clean 冷 3 轮里 **2 轮轮首 >4 触发本批作废线**（B256Cc01 4.87 / B64Cc01 4.68；B32Cc01 3.34 过）。
   **绝对吞吐数字不得跨会话引用**（QS §4 已量化 ±17%，本批环境更重）。
   同一 ambient 也是门里 `stackb` 墙钟断言今天会红的原因（§10.7：Parsec/VTEncoder + ZCode 渲染
   + WindowServer 常驻占 1–2 核，`uptime` 5-min 均值实测到 **10.97**——全量测试跑期间）。
3. **作废 3 轮的形态与 QS 不同**：QS 的 MISS =「未起下载」；本批 =「下载起了但 stall」（服务端只发出
   12.0/12.0/13.6 MB，轮内 loadavg 峰值 5.1–9.4）。已如实登记，不当作有效轮。
4. **1 Hz 采样是启动判决的硬限制**：出口 stoplog 逐秒 ⇒ 「首 RTT 团块」的**亚秒结构不可见**；
   本批的应对是用 `整形观测`（5 s 窗）的峰值滞留 + 均包/拍做机制侧证。要真看团块需要
   **包级抓包**——本机 `sudo` 需密码 ⇒ tcpdump 不可用（**登记为未取面**）。
5. **`pkt_s` 字段仍不可用**（QS §8-4 的笔误仍在补丁里，本批原样复用）：本记录一切包率均由相邻行
   `sent`/`udp_tx` 差重算。
6. **T6 的设备 PID**：冷档 App 重启换 pid（3772/4612/5423），只取轮内同 pid 差；MISS 轮不参与 T6。
7. **每轮重启出口 ⇒ 每轮都是新外层 QUIC 连接 + 新内层 TCP 连接**（与 QS 同规程）；「热」= App/隧道
   进程常驻（浏览器不在定义内 ⇒ §10.2 的浏览器 force-stop 不破坏热/冷语义）。
